### Terminology
- **Data:** Facts that can be recorded
- **Database**: Collection of data
- **Database Management System (DMBS):** Software for managing and storing databases
	- Apps <-> DBMS <-> Database (Containing shared data)
- **Data dictionary**: Stores the description of the *format* of the data


- Databases (and data) are assets to organisations
- Key business operations rely on accurate data
	- E.g Sales related industries rely heavily on accurate data

### Use of shared data:
-  Many applications within a system can use the same set of shared data
- Without centralised shared data, information can be stored in more than one place which can make inconsistencies if only one copy is edited and not all instances hard to track latest 'correct' information

### DBMS:
- Databases are stored/managed by DBMS
- Examples of large/commercial DBMS:
	- Oracle, MS SQLServer, IBM
- Smaller DMBS:
	- PostgreSQL, MySQL
- When users run applications, the application accesses data through the DBMS, which retrieves the necessary data and returns it to the application

### Concerns
- What data is necessary to keep
- Ensuring data isn't lost or destroyed
- Ensuring data is accurate and correct
- Restricting unauthorised access to data

### Relational DBMSs
- Simple structure
- Uniformly simple data, no duplicate rows
- Each entry is simple; integer, strings etc..
- [[Example Relational DBMS]]

### Schema
- Describes structure of data in a particular database
	- Tables
	- Column names, type
	- Integrity constraints (e.g. unique IDs, check conditions)
- The schema changes rarely, if at all
- Any database **instance** at any time must conform to the structure defined by the schema

### Instance
- The contents/state of the database at a single point in time
- Specific values describing a specific situation in the real world
- Every update, insert, or deletion changes the instance (dynamic, whereas schema is static)

## Data Design
- The process of deciding on the schema to be used for the database
- Proceeds in distinct stages:
	1. **Conceptual / Semantic Model**: High-level representation of entities and relationships
	2. **Relational Schema (Logical Model)**: Translation of conceptual model into relational tables, columns, and keys
	3. **Evaluation & Refinement**: Assessing schema quality (normalisation) and improving it

## Database Languages (SQL)
- For relational DBMSs, both DDL and DML are expressed in **SQL**:

### DDL (Data Definition Language)
- Used to define and alter the database schema
- Specifies what tables exist, their columns, data types, and integrity constraints
- Commands: `CREATE`, `ALTER`, `DROP`

### DML (Data Manipulation Language)
- Used to access and manipulate data within existing tables
- Commands for retrieving data (**queries**): `SELECT`
- Commands for modifying data: `INSERT`, `UPDATE`, `DELETE`
- **Declarative nature**: The programmer specifies **what** data is needed, not **how** to retrieve it
	- The DBMS query optimizer determines an execution strategy that is both correct and fast (e.g. choosing between scanning tables, using indexes, or reordering joins)

### SQL Query Examples:
```sql
-- Simple query: Find SuppID and Phone of supplier 'Heinz'
SELECT SuppID, Phone
FROM Supplier
WHERE SName = 'Heinz';

-- Aggregate query: Count products supplied by SuppID 8703
SELECT COUNT(*)
FROM Product
WHERE SuppID = 8703;

-- Join query: Show ProdID of products supplied by 'Heinz'
SELECT ProdID
FROM Supplier, Product
WHERE Product.SuppID = Supplier.SuppID
  AND Supplier.SName = 'Heinz';
```

## Three-Schema Architecture (Levels of Abstraction)
Provides data abstraction to hide storage details from users and applications:

1. **External Level (View Level)**:
	- Multiple user/application views
	- Describes how individual users or roles see the data
	- Provides customized interfaces and hides unnecessary or restricted data
2. **Conceptual Level (Logical Level)**:
	- Single global logical schema of the entire database shared among all users
	- Defines all entities, relationships, constraints, and data types
	- Independent of physical storage details and DBMS-specific storage mechanisms
3. **Internal Level (Physical Level)**:
	- Physical schema describing low-level storage
	- Files, pages, record layouts, compression, and indexes on disk

### Data Independence
- Applications are insulated from how data is structured and stored (no need to rewrite or recompile application code when underlying layers change)
- **Logical Data Independence**:
	- Protection from changes in the logical schema (e.g. adding a new column or table does not break existing views/queries)
- **Physical Data Independence**:
	- Protection from changes in physical storage structure or access methods (e.g. adding an index or reordering data on disk to speed up queries does not require changing application code)
- One of the most important benefits of using a DBMS

## Roles with DBMS
- **End Users**: Use applications to advance organisational goals; often unaware of the underlying DBMS
	- *Off-line naïve users*: Consume pre-generated reports (e.g. store manager reviewing weekly sales)
	- *Parametric naïve users*: Run pre-written applications with set inputs (e.g. deli clerk updating stock)
	- *Ad hoc users*: Explore data directly to discover trends or insights (e.g. division managers writing custom queries)
- **Application Programmers**:
	- Develop applications that access data through the DBMS
	- Require software engineering skills (SDLC, QA, UI design) combined with database querying
- **Database Administrator (DBA)**:
	- Responsible for the effective and efficient management of database resources
	- **Key tasks**:
		- *Schema design*: Design logical and physical schemas, balancing performance across all users
		- *Security & authorisation*: Manage user accounts, access permissions, and monitor security violations
		- *Data availability & crash recovery*: Ensure backups are taken and tested for recovery
		- *Performance tuning*: Monitor query performance, tune configurations, and adjust indexes/schemas
- **DBMS Vendor Staff**:
	- Build and support the DBMS software itself (e.g. Oracle, IBM, Microsoft)
	- Implementors, tool developers, support engineers, and technical trainers

## Big Ideas in Data Management
1. **Meta-data as Data**:
	- Data cannot be interpreted without its metadata (e.g. raw values like `162` are meaningless without knowing if it represents weight, height, room number, or hourly pay)
	- Stored centrally within the database itself in the **System Catalogue / Data Dictionary**
2. **"What" not "How" (Declarative Querying)**:
	- Users write declarative requests based on logic (`SELECT ... FROM ... WHERE ...`)
	- The DBMS automatically determines the most efficient procedural execution plan
3. **Administrative Services**:
	- Centralised management enables balancing global organisational needs, security, backup strategies, and resource allocation

## File System vs DBMS

### Drawbacks of Using File Systems:
- **Data Redundancy and Inconsistency**: Information duplicated across multiple files; updating one copy leads to conflicting records
- **Difficulty in Accessing Data**: Every new information need requires writing and compiling a new custom program
- **Lack of Central Metadata**: Data declarations are repeated in every program; changes to file format break all dependent programs
- **Integrity Problems**: Integrity constraints (e.g. `balance > 0`, foreign key checks) must be manually enforced in code by every application
- **Atomicity Problems**: Updates involving multiple steps (e.g. funds transfer) must be all-or-nothing; crashes mid-process leave files in corrupt or inconsistent states
- **Concurrent Access Anomalies**: Uncontrolled simultaneous access by multiple users causes race conditions and lost updates
- **Coarse Security**: File systems only offer coarse permissions (owner/group/world); cannot restrict access at column/row level

### Why Organisations Use a DBMS:
- Provides **data independence** and efficient automated query optimization
- Dramatically reduces **application development time**
- Centralises **data integrity constraints** and **fine-grained security / access control** (views and permissions)
- Enables reliable **concurrent multi-user access** and automated **crash recovery (ACID transactions)**
- Provides **uniform administration** and allows combining data from multiple sources

> [!NOTE]
> **Trade-offs of DBMS**:
> - Overhead in performance for trivial, simple processing tasks
> - Financial costs: licensing fees for commercial engines and salaries for skilled DBAs
> - Relational DBMSs are optimized for structured business data; highly specialized data (e.g. gene sequences, large multimedia) may require alternative specialized data models (graph, document, time-series)
