# Part A: ER Diagrams & Conceptual Modeling

## 1. Review: Relational Data & Schemas
- **Relational Model Fundamentals**:
  - Users see data as tables (relations) of uniformly structured records (tuples).
  - No duplicate rows, row order does not matter.
  - Entries are atomic (integers, strings, floats, dates).
  - Connections between tables are established through **matching values**.

### Schema Formats
- **Text Format**:
  - With types: `TableName(Col1: type, Col2: type, ...)`
  - Without types (implicit): `TableName(Col1, Col2, ...)`
- **Primary Key (PK)**:
  - An attribute (or minimal set of attributes) whose values uniquely identify every row.
  - Indicated in text schema by **underlining**:
    - `Product(`<u>`ProdID`</u>`: int, Descr: string, SuppID: int)`
- **Composite Primary Key**:
  - When no single column is unique on its own, a combination of columns forms the primary key.
  - All participating columns are underlined:
    - `SupplierCountryOffice(`<u>`SuppID`</u>`, `<u>`CountryCode`</u>`, StreetAddress, Postcode)`
- **Relational Schema Diagrams**:
  - Can be drawn with horizontal or vertical column listings.
  - **Rules**:
    1. **Underline** all primary key attributes.
    2. Draw a **directed arrow** from the referring column (foreign key) to the primary key identifier of the referenced table (`Dependent.fk -> Dominant.pk`).

## 2. Database Design Lifecycle
Database design follows a structured four-stage sequence:

| Stage | Activity | Key Focus |
| :--- | :--- | :--- |
| **1. Requirements Analysis** | Study business context *(ISYS2110)* | What data needs to be stored, what operations/apps are most frequent |
| **2. Conceptual Design** | Build conceptual model *(ISYS2120)* | High-level data description matching user mental model; DBMS-independent communication vehicle |
| **3. Logical Design** | Map to logical schema *(ISYS2120)* | Convert conceptual model into a relational database schema (tables, keys, FKs) |
| **4. Physical Design** | Physical schema & tuning *(ISYS2120)* | Storage allocation, indexing, performance tuning for specific DBMS workloads |

> [!NOTE]
> A conceptual data model specifies *what* data is stored, **not** how it is physically implemented, created, updated, or deleted.

## 3. The Entity-Relationship (ER) & Enhanced ER (EER) Model
- Originally proposed by **Peter Chen (1976)**; extended with object-oriented concepts (subclasses, inheritance, aggregation) to form the **Enhanced / Extended ER (EER)** model.
- In ISYS2120, "ER model" always refers to the **EER model**.

### 3.1 Entities and Entity Types
- **Entity (Entity Instance)**: A specific real-world person, place, object, event, or concept distinguishable from others (e.g. `John Doe`, unit `COMP5138`).
- **Entity Type (Entity Set)**: A collection of entities sharing common properties (e.g. `Student`, `Course`).
  - Represented by a **Rectangle**.
  - Entity sets do not need to be mutually disjoint.
- **Attribute**: A descriptive property of an entity type.
  - Represented by an **Ellipse** connected to the entity rectangle.
  - **Simple vs Composite**: Composite attributes have sub-components (e.g. `Address` $\rightarrow$ `street`, `suburb`, `postcode`; `Name` $\rightarrow$ `first`, `last`).
  - **Single-valued vs Multi-valued**: Multi-valued attributes can hold multiple values for one entity instance (e.g. `Hobbies`, `keywords`). Represented by a **Double Ellipse**.
  - **Primary Key**: Underlined attribute name within the ellipse.

### 3.2 Relationships
- **Relationship**: An association connecting two or more entity instances (e.g. "John is enrolled in ISYS2120").
  - Do **not** confuse an ER *relationship* with a relational model *relation* (table).
- **Relationship Type (Relationship Set)**: Set of similar relationships across the same entity types.
  - Represented by a **Diamond** connected to the participating entity rectangles.
- **Relationship Attributes**: Descriptive properties belonging to the relationship itself (e.g. `grade` or `enrolment_date` in `EnrolledIn`). Represented by an ellipse connected to the diamond.
- **Roles**: Labels on the edges connecting entities to relationships. Crucial for **recursive (unary)** relationships where an entity type is related to itself (e.g. `Employee` participates as `Manager` and `Subordinate` in `Supervises`).
- **Degree of Relationship**:
  - **Unary (Recursive)**: 1 entity type involved.
  - **Binary**: 2 entity types involved (most common).
  - **Ternary**: 3 entity types involved.

## 4. Multiplicity & Integrity Constraints (ISYS2120 Notation)

> [!IMPORTANT]
> Different textbooks (e.g. Cow book, Silberschatz, UML) use different diagram notations. In ISYS2120, follow the **Kifer/Bernstein/Lewis** notation strictly.

### 4.1 Key Constraint (Arrow $\rightarrow$)
- **Meaning**: An entity participates in **at most one** relationship instance ($0$ or $1$).
- **Notation**: Directed **arrow** from the entity rectangle pointing **towards the relationship diamond**.
- **Example**: `Subject` $\rightarrow$ `[WhereExamHeld]` — each subject has an exam in *at most one* room (Many-to-One / $N:1$ from Subject to Room).
- A plain line (no arrowhead) means **many** (no upper limit).

### 4.2 Participation Constraint (Thick Line)
- **Total Participation**: Every entity instance must participate in **at least one** relationship instance ($1$ or more).
  - Represented by a **Thick line** from the entity to the diamond.
- **Partial Participation**: Entity instance can exist without participating in the relationship ($0$ or more).
  - Represented by a standard **Thin line** (default).

### 4.3 Summary of Multiplicity Combinations

| Constraint Combination | Diagram Representation | Meaning |
| :--- | :--- | :--- |
| **Many-to-Many ($M:N$)** | Plain thin lines on both sides | Entities on both sides can participate in $0..*$ instances |
| **Many-to-One ($N:1$)** | Arrow $\rightarrow$ pointing to diamond from entity $A$ | Each $A$ is related to *at most one* $B$ |
| **Total Participation** | Thick line from entity $A$ to diamond | Each $A$ is related to *at least one* $B$ |
| **Key + Total (Exactly One)** | **Thick Arrow** ($\Rightarrow$) towards diamond | Each $A$ is related to **exactly one** $B$ |

## 5. Advanced EER Concepts

### 5.1 Weak Entities
- **Definition**: An entity type that does not have sufficient attributes to form its own primary key.
- **Identification**: Instances are identified in combination with an owner entity via an **identifying relationship** (which is a total $M:1$ relationship).
- **Discriminator (Partial Key)**: Attribute that distinguishes instances of the weak entity *belonging to the same owner*.
- **Notation**:
  - Weak Entity: **Double Rectangle**.
  - Identifying Relationship: **Double Diamond**.
  - Discriminator: **Dashed Underline** in the attribute ellipse.
  - *Example*: `Loan` (owning) $\xleftarrow{\text{thick}}$ `[[has]]` $\leftarrow$ `[[Payment]]` (weak), where `paymentNo` is dashed-underlined.

### 5.2 Generalisation / Specialisation (IsA Hierarchy)
- Arranges entity types into superclass/subclass hierarchies:
  - Subclass $F$ is a specialisation of Superclass $E$ ($F \subseteq E$).
  - Subclass inherits **all attributes** and **all relationship participations** of the superclass.
  - Subclasses only declare their specific, non-inherited attributes.
- **Notation**: A **Triangle labeled "ISA"** with superclass at the top and subclasses at the bottom.
- **Hierarchy Constraints**:
  - **Overlap Constraints**:
    - **Disjoint**: An entity instance belongs to at most one subclass. Noted with `disjoint` next to the triangle.
    - **Overlapping**: An entity instance can belong to multiple subclasses (default).
  - **Covering Constraints**:
    - **Total**: Every superclass instance must belong to at least one subclass. Represented by a **Thick line** between superclass and ISA triangle.
    - **Partial**: A superclass instance might not belong to any subclass (default, thin line).

### 5.3 Aggregation
- **Problem**: In ternary relationships, some entities/relationships may have independent associations (e.g. managing an employee's assignment to a job at a specific branch). Direct multiple relationships cause redundancy.
- **Solution**: Treats a relationship set (and participating entity sets) as a single higher-level abstract entity set.
- **Notation**: A **Dashed box** enclosing the relationship diamond and its entity types, which then participates as an endpoint in another relationship diamond.

# Part B: SQL Basics

## 1. SQL Overview
- **SQL (Structured Query Language)**: Standard declarative query language for relational DBMS.
  - *Declarative*: Specifies **what** data is required, not **how** to retrieve it.
- **Language Subdivisions**:
  - **DDL (Data Definition Language)**: Creates, modifies, drops schema objects (`CREATE`, `ALTER`, `DROP`).
  - **DML (Data Manipulation Language)**: Queries and manipulates data (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).
  - **DCL (Data Control Language)**: Manages permissions, users, and transactions (`GRANT`, `REVOKE`).

---

## 2. Fundamental `SELECT` Statement Structure
Every SQL `SELECT` query returns a **single relation** (table).

```sql
SELECT [DISTINCT | ALL] column1, column2, expression
FROM Table1 [alias1], Table2 [alias2]
WHERE condition
ORDER BY column1 [ASC | DESC], column2 [ASC | DESC];
```

### Clause Summary:
- **`SELECT`**: Specifies columns, expressions, or aggregates to return (projection).
- **`FROM`**: Specifies table(s) from which tuples are drawn (Cartesian product / joins).
- **`WHERE`**: Boolean predicate filtering which tuples appear in the result (selection).
- **`GROUP BY`**: Partitions tuples into groups (covered in Week 4).
- **`HAVING`**: Condition filtering groups (covered in Week 4).
- **`ORDER BY`**: Sorts output tuples (`ASC` ascending by default, `DESC` descending).

---

## 3. SQL Syntax Rules & Expressions

### 3.1 Identifiers & Literals
- **Case-Insensitivity**: SQL keywords and identifiers (table/column names) are case-insensitive.
- **No Hyphens**: Hyphens `-` are arithmetic minus operators and are **not permitted** in identifiers (use underscores `_`).
- **Strings**: String literals **must use single quotes** `'value'`. Double quotes `"..."` or curved quotes `’...’` cause syntax errors. String comparisons are case-sensitive.

### 3.2 Projections, Renaming, and Arithmetic
- **Select All Columns**: `SELECT * FROM Student;`
- **Arithmetic Expressions**: `+`, `-`, `*`, `/` on numeric attributes:
  ```sql
  SELECT uos_code, title, credit_points * 2, lecturer 
  FROM UnitOfStudy;
  ```
- **Renaming (`AS` clause)**: Assigns readable alias to output columns or tables:
  ```sql
  SELECT sid, mark AS score 
  FROM Assessment 
  WHERE uos_code = 'PHYS1001';
  ```

### 3.3 Duplicate Elimination (`DISTINCT`)
- Unlike pure relational algebra sets, SQL multiset tables permit duplicates.
- Default is `ALL` (preserves duplicates).
- Use `DISTINCT` to remove duplicate rows:
  ```sql
  SELECT DISTINCT country FROM Student;
  ```

### 3.4 Comments in SQL
- Single-line comment: `-- comment text`
- Multi-line / block comment: `/* comment text */`

---

## 4. `WHERE` Clause Filtering

### 4.1 Comparison & Logical Operators
- **Comparison**: `=`, `>`, `>=`, `<`, `<=`, `!=` (or `<>`).
- **Logical Connectives**: `AND`, `OR`, `NOT` (supports parentheses for precedence).
- **Range Operator (`BETWEEN ... AND ...`)**:
  - Boundaries are **inclusive**:
  ```sql
  SELECT sid FROM Assessment 
  WHERE uos_code = 'COMP5138' 
    AND mark BETWEEN 65 AND 74;
  ```
- **Set Membership (`IN`)**:
  ```sql
  SELECT sid FROM Enrolled 
  WHERE uos_code = 'ISYS2120' 
    AND grade IN ('DI', 'HD');
  ```

### 4.2 String Matching (`LIKE` & Regex)
- **`LIKE` Operator Wildcards**:
  - `%` : Matches zero or more arbitrary characters.
  - `_` : Matches exactly one character.
  - *Example*: Find all COMP units:
    ```sql
    SELECT title FROM UnitOfStudy WHERE uos_code LIKE 'COMP%';
    ```
- **Concatenation Operator**: `||` combines strings.
- **Regular Expressions (`regexp_like`)**:
  - SQL:2003 standard pattern matching function:
  ```sql
  SELECT title FROM UnitOfStudy 
  WHERE regexp_like(uos_code, '^COMP[0-9]{4}');
  ```

### 4.3 Date and Time
- **Types**: `DATE` (`'2026-03-26'`), `TIME` (`'16:12:05'`), `TIMESTAMP` (`'2026-03-26 16:12:05'`), `INTERVAL` (`'5 DAY'`).
- **Built-in System Values**: `CURRENT_DATE`, `CURRENT_TIME`.
- **Functions**:
  - `EXTRACT(YEAR FROM enroldate)`
  - Explicit date literals: `DATE '2026-03-01'`
  - Date arithmetic: `'2026-04-01' + INTERVAL '36 HOUR'`

## 5. Joining Multiple Tables

### 5.1 Cross Product vs Join Predicate
- Specifying multiple tables in `FROM` creates a Cartesian product ($R \times S$):
  ```sql
  SELECT * FROM Student, UnitOfStudy; -- All row pairs (rarely desired)
  ```
- To match related tuples, add a **join predicate** in `WHERE`:
  ```sql
  SELECT Student.sid, name, country
  FROM Student, Enrolled
  WHERE Student.sid = Enrolled.sid 
    AND uos_code = 'ISYS2120';
  ```

### 5.2 Table Aliasing & Self-Joins
- Aliases give concise names and allow joining a table to itself:
  ```sql
  -- Find each academic and their immediate manager
  SELECT A.name AS academic, M.name AS manager
  FROM Academic A, Academic M
  WHERE A.manager = M.empid;
  ```

### 5.3 Explicit SQL Join Operators
- **`NATURAL JOIN`**: Joins on all columns with identical names across both tables (removes duplicate columns automatically):
  ```sql
  SELECT name, uos_code, semester 
  FROM Student NATURAL JOIN Enrolled;
  ```
- **`JOIN ... ON`**: Explicit condition join:
  ```sql
  SELECT name 
  FROM UnitOfStudy JOIN Academic ON lecturer = empid
  WHERE uos_code = 'ISYS2120';
  ```
- **`JOIN ... USING (col1, ...)`**: Joins on specific shared columns.

## 6. Aggregate Functions
Aggregate functions take a multiset of values from a column across multiple rows and compute a single summary value:

| Function | Description |
| :--- | :--- |
| `COUNT(*)` | Number of rows matching the `WHERE` condition |
| `COUNT(col)` | Number of non-null values in column |
| `SUM(col)` | Sum of numerical values |
| `AVG(col)` | Arithmetic average of values |
| `MIN(col)` | Minimum value |
| `MAX(col)` | Maximum value |

### Combining with `DISTINCT`:
- By default aggregates operate on all values (multiset).
- To ignore duplicate values in aggregates, pass `DISTINCT`:
  ```sql
  -- Count how many unique Australian students are enrolled in any class
  SELECT COUNT(DISTINCT sid)
  FROM Student NATURAL JOIN Enrolled
  WHERE country = 'AUS';
  ```

> [!WARNING]
> **Common Pitfall**: You **cannot** mix a non-aggregate column and an aggregate function in `SELECT` without a `GROUP BY` clause.
> ```sql
> -- INVALID: sid produces multiple rows while max(mark) produces one scalar
> SELECT sid, max(mark) FROM Assessment WHERE uos_code = 'SOFT2007';
> ```
