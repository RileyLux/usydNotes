# Part A: Relational Algebra (RA)

## 1. Motivation & The Big Idea
- **Declarative vs. Procedural Querying**:
  - **SQL is Declarative**: A user states *what* data to retrieve, not *how* to physically compute it.
  - **Relational Algebra is Procedural**: It prescribes an exact, step-by-step mathematical recipe (*how*) to derive a new relation from existing relations using operators.
- **Why Does Relational Algebra Matter?**:
  - **Equivalent Formulations**: The same information request can be written in many syntactically different ways in SQL (e.g. joins vs. nested subqueries vs. Cartesian products with filters).
  - **Internal DBMS Execution**: A relational DBMS translates incoming declarative SQL queries into an internal algebraic expression (represented as a **Query Tree** / **Logical Query Plan**).
  - **Query Optimization**: The DBMS query optimizer applies mathematical **equivalence rules** (rewrite rules) to transform inefficient algebraic trees into equivalent plans with drastically lower computational and I/O costs.

```
                  [ Declarative SQL Query ]
                              │
                              ▼
                       [ SQL Parser ]
                              │
                              ▼
               [ Initial Relational Algebra Plan ]
                              │
                              ▼
              [ Relational Query Optimizer ]
        (Applies RA Equivalence Rules, pushes selections)
                              │
                              ▼
               [ Optimized Physical Plan ]
                              │
                              ▼
                   [ Execution Engine ]
```

- **The Relational Closure Property**:
  - Every operator in relational algebra takes one or more relations as input and produces **a new relation** as its output.
  - Because the output is always a relation, operations can be **arbitrarily nested and composed** into complex query expressions.

---

## 2. Mathematical Definition of Relations vs. Real-World RDBMS

### 2.1 Mathematical Relation (Discrete Mathematics)
- Given $n$ domains (sets of values) $D_1, D_2, \dots, D_n$:
  $$\text{Relation } R \subseteq D_1 \times D_2 \times \dots \times D_n$$
- A relation $R$ is a **mathematical set** of $n$-tuples $(a_1, a_2, \dots, a_n)$, where each element $a_i \in D_i$.
- **Example**:
  - If $\text{StudentID} = \{1001, 1002, 1003\}$, $\text{Name} = \{\text{Alice}, \text{Bob}\}$, $\text{Country} = \{\text{AUS}, \text{CHN}\}$,
  - Then $R = \{(1001, \text{Alice}, \text{AUS}), (1002, \text{Bob}, \text{CHN})\}$ is a relation over $\text{StudentID} \times \text{Name} \times \text{Country}$.

### 2.2 Mathematical Model vs. Practical SQL RDBMS

| Feature | Mathematical Relation | SQL Relational Database (RDBMS) |
| :--- | :--- | :--- |
| **Duplicates** | **Strictly prohibited** (Sets cannot contain duplicate elements). | **Permitted** by default (Tables operate as **multisets / bags** unless `DISTINCT` or `PRIMARY KEY` is enforced). |
| **Row Ordering** | **Unordered** (Set elements have no natural sequence). | **Unordered logically**, but physical storage order exists and deterministic output order is achieved via `ORDER BY`. |
| **Missing Values** | **Not permitted** (Every tuple entry is a concrete domain element). | **Permitted** (`NULL` represents unknown, unrecorded, or inapplicable information). |
| **Domains / Datatypes** | Can be arbitrary mathematical sets (finite or infinite). | Restricted to a predefined set of simple, atomic scalar datatypes (`INT`, `VARCHAR`, `DATE`, etc.). |
| **Attribute Identification** | Historically indexed by positional coordinate ($1^{\text{st}}, 2^{\text{nd}}, \dots, n^{\text{th}}$). | Named attributes/columns with explicit logical schema labels. |

## 3. The 6 Fundamental (Basic) Operators
Any relational query can be formulated using a minimal kernel of **six basic operators**:
1. **Selection** ($\sigma$)
2. **Projection** ($\pi$)
3. **Cartesian Product** ($\times$)
4. **Set Union** ($\cup$)
5. **Set Difference** ($-$)
6. **Rename** ($\rho$)

---

### 3.1 Selection ($\sigma$) — Horizontal Partitioning
- **Purpose**: Picks a subset of rows (tuples) from an input relation that satisfy a specified boolean condition.
- **Notation**:
  $$\sigma_{\text{predicate}}(R) \quad \text{or in plain text:} \quad \text{SELECT}_{\{\text{predicate}\}}(R)$$
- **Condition / Predicate**:
  - Boolean combinations of comparisons using attribute names, constants, arithmetic operators, comparison operators ($=, \neq, <, \le, >, \ge$), and logical connectives ($\land, \lor, \neg$).
- **Schema**: The resulting relation has the **exact same schema and attributes** as the input relation $R$.
- **Example**:
  $$\sigma_{\text{country} = \text{'AUS'}}(\text{Student})$$
  Filters rows in `Student` to retain only Australian students.

---

### 3.2 Projection ($\pi$) — Vertical Partitioning
- **Purpose**: Extracts specified columns (attributes) from an input relation and discards the remaining columns.
- **Notation**:
  $$\pi_{A_1, A_2, \dots, A_k}(R) \quad \text{or in plain text:} \quad \text{PROJECT}_{\{A_1, A_2, \dots, A_k\}}(R)$$
- **Duplicate Elimination**: Because pure relational algebra adheres to mathematical set semantics, any duplicate tuples resulting from removing distinguishing columns are **automatically eliminated**.
- **Schema**: The result schema contains **only** the attributes listed in the projection list $[A_1, A_2, \dots, A_k]$.
- **Example**:
  $$\pi_{\text{name, country}}(\text{Student})$$
  Returns a two-column relation containing unique `(name, country)` pairs.

---

### 3.3 Cartesian Product / Cross-Product ($\times$)
- **Purpose**: Combines every tuple of relation $R$ with every tuple of relation $S$.
- **Formal Definition**:
  $$R \times S = \{ (t, s) \mid t \in R \land s \in S \}$$
- **Dimensions**:
  - **Arity (Degree)**: $\text{deg}(R \times S) = \text{deg}(R) + \text{deg}(S)$ (sum of columns).
  - **Cardinality**: $|R \times S| = |R| \times |S|$ (product of row counts).
- **Naming Conflicts**: If $R$ and $S$ have columns sharing the same name, attribute references must be disambiguated using qualified names ($R.A$, $S.A$) or the Rename operator.

---

### 3.4 Set Union ($\cup$)
- **Purpose**: Returns all tuples that appear in $R$, in $S$, or in both relations. Duplicates are removed.
- **Formal Definition**:
  $$R \cup S = \{ t \mid t \in R \lor t \in S \}$$
- **Union-Compatibility Condition**:
  - Both relations must have the **same arity** (identical number of attributes).
  - Corresponding attributes (by position) must share **compatible domains/datatypes**.

---

### 3.5 Set Difference ($-$)
- **Purpose**: Returns tuples that belong to relation $R$ but **do not** belong to relation $S$.
- **Formal Definition**:
  $$R - S = \{ t \mid t \in R \land t \notin S \}$$
- **Properties**:
  - Requires **union-compatibility**.
  - **Non-commutative**: In general, $R - S \neq S - R$.

---

### 3.6 Rename ($\rho$)
- **Purpose**: Assigns a new name to a relation instance or renames individual attributes within a relation.
- **Why It Is Essential**:
  - Disambiguates duplicate attribute names when taking Cartesian products.
  - Allows an expression to be referenced multiple times (e.g. self-joins).
- **Notation Variants**:
  - **Rename Relation**: $\rho_{X}(E)$ returns the result of expression $E$ under relation name $X$.
  - **Rename Attributes**: $\rho_{X(A_1 \to B_1, A_2 \to B_2, \dots)}(E)$ renames attribute $A_i$ to $B_i$.
  - **Positional Rename**: $\rho_{X(B_1, B_2, \dots, B_n)}(E)$ renames all $n$ columns in order.
- **Example**:
  $$\rho_{\text{Classlist}(\text{sid} \to \text{student})}(\sigma_{\text{uos\_code} = \text{'ISYS2120'}}(\text{Enrolled}))$$

---

## 4. Derived Operators
Derived operators add no theoretical expressive power over the 6 basic operators, but serve as concise, readable shorthand for recurring patterns.

### 4.1 Set Intersection ($\cap$)
- **Purpose**: Returns tuples present in both $R$ and $S$.
- **Derivation from Basic Operators**:
  $$R \cap S = R - (R - S)$$
  *(Alternatively: $R \cap S = (R \cup S) - ((R - S) \cup (S - R))$)*
- **Requirement**: $R$ and $S$ must be union-compatible.

---

### 4.2 Theta-Join / Conditional Join ($\bowtie_C$)
- **Purpose**: Pairs tuples from $R$ and $S$ that satisfy a specified join condition $C$.
- **Derivation**:
  $$R \bowtie_C S = \sigma_C(R \times S)$$
- The schema of $R \bowtie_C S$ is identical to the schema of $R \times S$.

---

### 4.3 Equi-Join
- A specialized theta-join where the condition $C$ consists **exclusively of equalities** between attributes:
  $$R \bowtie_{R.A = S.B \land R.C = S.D} S$$
- Note: Both columns ($R.A$ and $S.B$) appear in the output relation schema.

---

### 4.4 Natural Join ($\bowtie$)
- **Purpose**: Performs an equi-join equating **all attributes that share the exact same name** between $R$ and $S$, and projects out the duplicate columns so that only **one copy** of each shared attribute is retained.
- **Formal Behavior**:
  - Let common attributes be $X = \text{Attr}(R) \cap \text{Attr}(S)$.
  - Let unique attributes be $Y = \text{Attr}(R) - X$ and $Z = \text{Attr}(S) - X$.
  - Natural join equates $R.X = S.X$ and produces schema $(X, Y, Z)$:
    $$R \bowtie S = \pi_{X, Y, Z}(\sigma_{R.X = S.X}(R \times S))$$
- If $R$ and $S$ have no common attribute names, $R \bowtie S = R \times S$ (degenerates to Cartesian product).

---

### 4.5 Relational Division ($\div$ or $/$)
- **Purpose**: Solves universal quantification problems — answering queries of the form **"Find items in set $A$ that are associated with ALL elements of set $B$"**.
  - *Examples*:
    - "Find students who have taken **all** core units."
    - "Find suppliers who supply **every** red part."
    - "Find customers who have ordered **all** books written by Tolkien."
- **Terminological Convention**:
  - In $R \div S$:
    - $R(A_1, \dots, A_n, B_1, \dots, B_m)$ is the **dividend** (candidate pairs).
    - $S(B_1, \dots, B_m)$ is the **divisor** (the required base set).
    - The output schema is strictly $(A_1, \dots, A_n)$ (the quotient).

#### Formal Definition
$$R \div S = \{ a \mid \forall b \in S, (a, b) \in R \}$$

#### Expressing Division via Basic Operators
How do we compute universal quantification using only selection, projection, product, and set difference?
We reformulate the problem into **negated set difference** (finding candidates that have **no missing items**):
1. **Find all possible candidate identities**:
   $$C = \pi_A(R)$$
2. **Generate all ideal combinations** (what candidates would have if they were paired with *every* item in $S$):
   $$\text{AllPairs} = \pi_A(R) \times S$$
3. **Find the disqualified pairs** (pairs that candidates are *expected* to have, but do *not* actually have in $R$):
   $$\text{MissingPairs} = (\pi_A(R) \times S) - R$$
4. **Identify the disqualified candidates** (candidates missing at least one required item):
   $$\text{Disqualified} = \pi_A((\pi_A(R) \times S) - R)$$
5. **Subtract disqualified candidates from all candidates**:
   $$R \div S = \pi_A(R) - \pi_A((\pi_A(R) \times S) - R)$$

#### Step-by-Step Division Example (Supplier & Parts)
Consider table $R(\text{sno}, \text{pno})$:

| sno | pno |
| :--- | :--- |
| `s1` | `p1` |
| `s1` | `p2` |
| `s1` | `p3` |
| `s1` | `p4` |
| `s2` | `p1` |
| `s2` | `p2` |
| `s3` | `p2` |
| `s4` | `p2` |
| `s4` | `p4` |

- **Case 1**: $S_1 = \{\text{pno}: \text{p2}\}$
  - Suppliers associated with `p2`: $\{s1, s2, s3, s4\}$.
- **Case 2**: $S_2 = \{\text{pno}: \text{p2}, \text{p4}\}$
  - Suppliers associated with *both* `p2` and `p4`: $\{s1, s4\}$.
- **Case 3**: $S_3 = \{\text{pno}: \text{p1}, \text{p2}, \text{p4}\}$
  - Suppliers associated with *all three* `p1`, `p2`, `p4`: $\{s1\}$.

## 5. Relational Algebra Equivalence Rules (Query Optimization)
Equivalence rules allow a DBMS query optimizer to mechanically transform one relational algebra expression into another that produces the **exact same relation instance**, but can be executed significantly faster.

```
       Unoptimized Tree (Join First)           Optimized Tree (Push Selection Down)
                 π_name                                      π_name
                   │                                           │
          σ_country='AUS'                                      ⋈_sid
                   │                                         ┌───┴───┐
                 ⋈_sid                                σ_country='AUS' Enrolled
               ┌───┴───┐                                     │
            Student  Enrolled                             Student
       (Large intermediate join)                   (Filters Student before join)
```

### 5.1 Commutation Rules
- **Projection & Selection Commutation**:
  $$\pi_A(\sigma_p(R)) = \sigma_p(\pi_A(R)) \quad \text{provided predicate } p \text{ references only attributes in } A$$
- **Join Commutativity**:
  $$R \bowtie_C S = S \bowtie_C R$$

### 5.2 Associativity Rules
- **Join & Cross-Product Associativity**:
  $$(R \bowtie S) \bowtie T = R \bowtie (S \bowtie T)$$
  $$(R \times S) \times T = R \times (S \times T)$$

### 5.3 Idempotence Rules
- **Cascade of Projections**:
  $$\pi_{A}(\pi_{B}(R)) = \pi_{A}(R) \quad \text{where } A \subseteq B$$
- **Cascade of Selections**:
  $$\sigma_{p_1}(\sigma_{p_2}(R)) = \sigma_{p_1 \land p_2}(R)$$

### 5.4 Distribution Rules (Crucial for Query Optimization)
- **Pushing Selection into Join / Cartesian Product**:
  $$\sigma_p(R \bowtie S) = \sigma_p(R) \bowtie S \quad \text{when } p \text{ mentions only attributes belonging to } R$$
  > [!TIP]
  > **Pushing selections down** is the single most important heuristic in relational query optimization. Filtering rows *before* performing an expensive join drastically shrinks the intermediate relations.
- **Pushing Projection into Join**:
  $$\pi_{A \cup B}(R \bowtie S) = \pi_A(R) \bowtie \pi_B(S) \quad \text{when all join attributes belong to } A \cap B$$
- **Distribution over Set Union**:
  $$\sigma_p(R \cup S) = \sigma_p(R) \cup \sigma_p(S)$$
  $$\pi_A(R \cup S) = \pi_A(R) \cup \pi_A(S)$$
  $$R \bowtie (S \cup T) = (R \bowtie S) \cup (R \bowtie T)$$

## 6. Translation & Conversion Skills

### 6.1 Mapping SQL Select-From-Where (SFW) to Relational Algebra
Every canonical single-block SQL query translates directly into a sequence of relational algebra operators:

```sql
SELECT A1, A2, ..., An
FROM R1, R2, ..., Rm
WHERE condition;
```
Translates to:
$$\pi_{A_1, A_2, \dots, A_n} \Big( \sigma_{\text{condition}} ( R_1 \times R_2 \times \dots \times R_m ) \Big)$$

> [!WARNING]
> **Naming Inversion Pitfall**:
> - The SQL `SELECT` clause corresponds to the Relational Algebra **Projection** ($\pi$) operator!
> - The Relational Algebra **Selection** ($\sigma$) operator corresponds to the SQL `WHERE` clause!

### 6.2 Stating the Purpose of RA Expressions (Exam Guideline)
When asked to describe an expression like:
$$\pi_{\text{name}}(\sigma_{\text{country} = \text{'AUS'}}(\text{Student}))$$
- **Correct (Full Marks)**: State the high-level business/user goal:
  *"Find the names of all Australian students."*
- **Incorrect (Zero / Poor Marks)**: Merely reciting the mathematical operator steps:
  *"Select rows where country equals 'AUS' and then project the name column."*

# Part B: Advanced SQL & Query Evaluation

## 1. Grouping and Aggregation (`GROUP BY` & `HAVING`)

### 1.1 Conceptual Partitioning
- The `GROUP BY` clause groups tuples that share identical values across one or more specified grouping columns into disjoint partitions.
- Aggregate functions (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) compute a single summary value per group.

```
Original Table Rows                       Partitioned Groups                   Aggregate Output
┌───────────────────────┐                 ┌───────────────────────┐            ┌───────────────┐
│ uos_code │ mark       │                 │ COMP5138: [60, 78]    │ ── AVG ──▶ │ COMP5138 │ 69 │
│ COMP5138 │ 60         │  ── GROUP BY ─▶ ├───────────────────────┤            ├───────────────┤
│ COMP5138 │ 78         │     uos_code    │ INFO6007: [85]        │ ── AVG ──▶ │ INFO6007 │ 85 │
│ INFO6007 │ 85         │                 └───────────────────────┘            └───────────────┘
└───────────────────────┘
```

### 1.2 The Golden Syntactic Rule of SQL Grouping
> [!IMPORTANT]
> **The Grouping Column Invariant**:
> Any column that appears in the `SELECT` list that is **not** enclosed inside an aggregate function **must** appear in the `GROUP BY` list!
>
> *Why?* If a table has multiple rows with different `studID` values inside the same `uos_code` group, executing `SELECT uos_code, studID, AVG(mark) ... GROUP BY uos_code` would force the DBMS to choose an arbitrary, ambiguous `studID` to pair with the single average mark, violating relational integrity.

```sql
-- INVALID: studID is not in GROUP BY and not aggregated
SELECT uos_code, studID, AVG(mark)
FROM Assessment
GROUP BY uos_code;

-- VALID: Every non-aggregated select column is in GROUP BY
SELECT uos_code, semester, AVG(mark)
FROM Assessment
GROUP BY uos_code, semester;
```

---

### 1.3 `HAVING` vs. `WHERE`
- **`WHERE`**:
  - Applied **before** grouping occurs.
  - Filters individual source tuples.
  - **Cannot** contain aggregate functions (e.g. `WHERE AVG(mark) > 50` is illegal).
- **`HAVING`**:
  - Applied **after** groups are formed and aggregate calculations are performed.
  - Filters entire groups based on group-level criteria (grouping attributes or aggregate predicates).

```sql
SELECT uos_code AS unit_of_study, AVG(mark)
FROM Assessment
GROUP BY uos_code
HAVING AVG(mark) > 65;
```

---

### 1.4 Conceptual Query Evaluation Order
SQL queries are evaluated in a logical pipeline that differs fundamentally from the order in which keywords are written:

```
 1. FROM        Identify involved tables, Cartesian products, and JOIN conditions
    │
    ▼
 2. WHERE       Filter individual rows fulfilling predicate conditions
    │
    ▼
 3. GROUP BY    Partition remaining rows into groups by grouping attributes
    │
    ▼
 4. HAVING      Filter out aggregated groups that fail the group predicate
    │
    ▼
 5. SELECT      Evaluate expressions, compute aggregates, and project columns
    │
    ▼
 6. ORDER BY    Sort the final result tuples
```

#### Detailed Pipeline Trace
**Query**:
```sql
SELECT uos_code AS unit_of_study, AVG(mark)
FROM Assessment NATURAL JOIN UnitOfStudy
WHERE credit_points = 6
GROUP BY uos_code
HAVING COUNT(*) >= 2;
```
1. **`FROM`**: Natural join joins `Assessment` and `UnitOfStudy` on shared attribute `uos_code`.
2. **`WHERE`**: Filters out rows where `credit_points <> 6`.
3. **`GROUP BY`**: Partitions remaining tuples by unique `uos_code`.
4. **`HAVING`**: Counts rows per group; discards any unit with fewer than 2 assessment records.
5. **`SELECT`**: Calculates `AVG(mark)` for each qualifying group and outputs `(unit_of_study, AVG)`.

### 1.5 Alternative Formulation: Grouped Subquery in `FROM`
Instead of using `HAVING`, an inner query in the `FROM` clause can perform grouping, allowing the outer query to filter group aggregates in a standard `WHERE` clause:
```sql
SELECT unit_of_study, avg_mark
FROM (
    SELECT number AS unit_of_study,
           AVG(mark) AS avg_mark,
           COUNT(*) AS studentcount
    FROM Assessment
    GROUP BY number
) AS Result
WHERE studentcount > 10;
```

## 2. Set Operations in SQL (`UNION`, `INTERSECT`, `EXCEPT`)
SQL provides set operators corresponding to relational algebra $\cup, \cap, -$:
- `UNION`: Set union.
- `INTERSECT`: Set intersection.
- `EXCEPT`: Set difference (*Note: Oracle uses `MINUS`*).

### 2.1 Set vs. Multiset (Bag) Semantics
- By default, `UNION`, `INTERSECT`, and `EXCEPT` **eliminate all duplicate rows**.
- To preserve duplicates, append the `ALL` keyword: `UNION ALL`, `INTERSECT ALL`, `EXCEPT ALL`.

| Operator | Result Multiplicity (Row occurs $m$ times in $R$, $n$ times in $S$) |
| :--- | :--- |
| `R UNION ALL S` | $m + n$ occurrences |
| `R INTERSECT ALL S` | $\min(m, n)$ occurrences |
| `R EXCEPT ALL S` | $\max(0, m - n)$ occurrences |

### 2.2 Concrete Banking Examples
```sql
-- Customers who have an account, a loan, or both (Duplicates removed)
(SELECT customer_name FROM depositor)
UNION
(SELECT customer_name FROM borrower);

-- Customers who have BOTH an account AND a loan
(SELECT customer_name FROM depositor)
INTERSECT
(SELECT customer_name FROM borrower);

-- Customers who have an account BUT NO loan
(SELECT customer_name FROM depositor)
EXCEPT
(SELECT customer_name FROM borrower);
```

## 3. The `NULL` Value in Query Processing & Three-Valued Logic (3VL)

### 3.1 Testing for NULL
`NULL` denotes absent, unknown, or inapplicable values.
> [!CAUTION]
> Never compare a column to NULL using `=` or `<>` (`grade = NULL` or `grade <> NULL`).
> Comparisons with `NULL` always evaluate to `UNKNOWN`. You **must** use the explicit predicates `IS NULL` and `IS NOT NULL`:
> ```sql
> SELECT sid FROM Enrolled WHERE grade IS NULL;
> ```

### 3.2 Three-Valued Logic (3VL) Truth Tables
SQL predicates evaluate to one of three truth values: `TRUE`, `FALSE`, or `UNKNOWN`.

| A | B | A AND B | A OR B |
| :---: | :---: | :---: | :---: |
| `TRUE` | `UNKNOWN` | `UNKNOWN` | `TRUE` |
| `FALSE` | `UNKNOWN` | `FALSE` | `UNKNOWN` |
| `UNKNOWN` | `UNKNOWN` | `UNKNOWN` | `UNKNOWN` |

| A | NOT A |
| :---: | :---: |
| `TRUE` | `FALSE` |
| `FALSE` | `TRUE` |
| `UNKNOWN` | `UNKNOWN` |

### 3.3 Acceptance Rule in `WHERE` and `HAVING`
- A row or group is included in the output **if and only if** the selection predicate evaluates strictly to **`TRUE`**.
- Rows evaluating to **`FALSE`** or **`UNKNOWN`** are discarded.
- **Trap**:
  ```sql
  SELECT sid FROM Enrolled WHERE grade <> 'DI';
  ```
  If a student has `grade = NULL`, the condition `NULL <> 'DI'` evaluates to `UNKNOWN`. Therefore, this student is **not returned** by the query!

### 3.4 Aggregates and `NULL`
- **`COUNT(*)`**: Counts every row in the partition/table, regardless of whether columns contain `NULL`.
- **`COUNT(column)`**: Counts only rows where `column` is **non-NULL**.
- **`AVG`, `SUM`, `MIN`, `MAX`**: Silently **ignore** all `NULL` values.
  - If a column contains only `NULL`s, `AVG`, `SUM`, `MIN`, and `MAX` evaluate to `NULL` (while `COUNT` evaluates to `0`).

### 3.5 `NULL` in `GROUP BY`
- When forming groups, all rows containing `NULL` in a grouping attribute are placed together into a **single group**.

## 4. Outer Joins
Inner joins discard any tuples that lack a matching record in the joined relation. Outer joins preserve non-matching tuples by padding missing attributes with `NULL`.

```
Relation Loan                            Relation Borrower
┌─────────────┬─────────────┬────────┐   ┌───────────────┬─────────────┐
│ branch_name │ loan_number │ amount │   │ customer_name │ loan_number │
├─────────────┼─────────────┼────────┤   ├───────────────┼─────────────┤
│ Downtown    │ L-170       │ 3000   │   │ Jones         │ L-170       │
│ Redwood     │ L-230       │ 4000   │   │ Smith         │ L-230       │
│ Perryridge  │ L-260       │ 1700   │   │ Hayes         │ L-155       │
└─────────────┴─────────────┴────────┘   └───────────────┴─────────────┘
(L-260 has no borrower)                  (L-155 has no loan record)
```

### 4.1 Join Types Comparison

| Join Syntax | Preserved Tuples | Description |
| :--- | :--- | :--- |
| `loan INNER JOIN borrower ON ...` | Matches only | Discards `L-260` and `L-155`. Returns only `L-170` and `L-230`. |
| `loan LEFT OUTER JOIN borrower ON ...` | All Left (`loan`) | Preserves `L-260`; customer columns padded with `NULL`. |
| `loan RIGHT OUTER JOIN borrower ON ...` | All Right (`borrower`) | Preserves `L-155`; loan amount/branch padded with `NULL`. |
| `loan FULL OUTER JOIN borrower ON ...` | All Both | Preserves both `L-260` and `L-155` with corresponding `NULL`s. |

### 4.2 Join Condition Syntax
- **`ON <predicate>`**: General condition (e.g. `ON loan.loan_number = borrower.loan_number`).
- **`USING (column_list)`**: Equi-join on specified shared columns; condenses duplicate columns into a single column in the output.
- **`NATURAL [INNER | LEFT | RIGHT | FULL] JOIN`**: Implicitly equates all columns with identical names.

## 5. Nested Subqueries

### 5.1 Subquery Types
1. **Non-Correlated Subquery**:
   - Completely self-contained; does not reference columns from the outer query.
   - Evaluated **once**, and its static result set is reused by the outer query.
   ```sql
   SELECT name
   FROM Student
   WHERE sid IN (
       SELECT sid FROM Enrolled WHERE uos_code = 'ISYS2120'
   );
   ```

2. **Correlated Subquery**:
   - References one or more columns from the outer query tuple (via table aliases).
   - Conceptually re-evaluated **for every candidate row** processed by the outer query.
   ```sql
   SELECT s.name
   FROM Student s
   WHERE EXISTS (
       SELECT 1 FROM Enrolled e
       WHERE e.sid = s.sid AND e.uos_code = 'ISYS2120'
   );
   ```

### 5.2 Set Comparison Operators

| Operator | Usage / Semantics | Example |
| :--- | :--- | :--- |
| `IN` / `NOT IN` | Tests whether an attribute value belongs to the set returned by the subquery. | `sid IN (SELECT sid FROM ...)` |
| `EXISTS` / `NOT EXISTS` | Evaluates to `TRUE` if the subquery returns at least one row (checks non-emptiness). | `WHERE NOT EXISTS (SELECT * FROM ...)` |
| `> ALL(subquery)` | Evaluates to `TRUE` if the value is strictly greater than **every single value** in the subquery (i.e. greater than the maximum). | `salary > ALL (SELECT salary FROM ...)` |
| `> ANY(subquery)` / `> SOME` | Evaluates to `TRUE` if the value is greater than **at least one value** in the subquery (i.e. greater than the minimum). | `mark > ANY (SELECT mark FROM ...)` |

> [!CAUTION]
> **The Dangerous `NOT IN` and `NULL` Trap**:
> If the subquery in a `WHERE x NOT IN (SELECT y FROM ...)` returns even a single `NULL` value, the condition evaluates to `UNKNOWN` for any $x$ that does not match a non-null $y$, causing the entire outer query to return **zero rows**!
> Prefer **`NOT EXISTS`**, which tests for the presence of rows and is completely immune to this `NULL` pitfall.

## 6. Universal Quantification ("For Every" Queries) in SQL
SQL lacks a built-in `FORALL` keyword. To express relational division ("Find entities related to *all* elements of a target set"), database developers utilize three alternative design patterns.

**Target Question**:
*"Find the names of students who have enrolled in **every** second-year ISYS unit of study (`uos_code LIKE 'ISYS2%'`)."*

### Pattern 1: Double `NOT EXISTS` (Negated Existential Quantification)
Based on the first-order logic identity:
$$\forall x \, P(x) \iff \neg \exists x \, (\neg P(x))$$
*"Find students for whom there does NOT exist a second-year ISYS unit that the student did NOT take."*

```sql
SELECT DISTINCT S.name
FROM Student S
WHERE NOT EXISTS (
    -- Set of all second-year ISYS units
    SELECT *
    FROM UnitOfStudy U
    WHERE U.uosCode LIKE 'ISYS2%'
      AND NOT EXISTS (
          -- Check if student S took unit U
          SELECT 1
          FROM Enrolled E
          WHERE E.studId = S.studId
            AND E.uosCode = U.uosCode
      )
);
```

### Pattern 2: `NOT EXISTS` with Set Difference (`EXCEPT`)
*"Find students for whom the set of (All 2nd-year ISYS units) EXCEPT (Units taken by this student) is EMPTY."*

```sql
SELECT S.name
FROM Student S
WHERE NOT EXISTS (
    SELECT uosCode
    FROM UnitOfStudy
    WHERE uosCode LIKE 'ISYS2%'
    EXCEPT
    SELECT E.uosCode
    FROM Enrolled E
    WHERE E.studId = S.studId
);
```

### Pattern 3: Group Aggregation Count Comparison
*"Count the number of qualifying units taken by each student and compare with the total count of required units."*

```sql
SELECT S.name
FROM Student S
JOIN Enrolled E ON S.studId = E.studId
WHERE E.uosCode LIKE 'ISYS2%'
GROUP BY S.studId, S.name
HAVING COUNT(DISTINCT E.uosCode) = (
    SELECT COUNT(*)
    FROM UnitOfStudy
    WHERE uosCode LIKE 'ISYS2%'
);
```

> [!WARNING]
> **Brainteaser: Repeated Enrollments**:
> If a student repeats a course, a naive `HAVING COUNT(*) = ...` will count multiple enrollments for the same subject, falsely satisfying the equality!
> - **Fix**: You **must** use `COUNT(DISTINCT E.uosCode)` and group by the primary key `S.studId, S.name`.

### Exercise 1: Lowest Credit Point Courses Lectured by Alan Fekete
> **Question**: How many courses are there with the lowest credit_point value, among the courses lectured by Alan Fekete?

```sql
SELECT COUNT(uoscode)
FROM courses
WHERE lecturer IN (
    SELECT empid
    FROM lecturers
    WHERE name = 'Alan Fekete'
)
AND credit_points = (
    SELECT MIN(credit_points)
    FROM courses
    WHERE lecturer IN (
        SELECT empid
        FROM lecturers
        WHERE name = 'Alan Fekete'
    )
);
```
- *Note*: `COUNT(DISTINCT uoscode)` is redundant since `uoscode` is the primary key of `courses`.

### Exercise 2: Student Mark Above Course Average
> **Question**: Find the name of student(s) whose mark on an assessment in a course is above the average mark for assessments in that course.

```sql
SELECT s.name
FROM students s
JOIN assessment a1 ON s.sid = a1.sid
WHERE a1.mark > (
    SELECT AVG(a2.mark)
    FROM assessment a2
    WHERE a2.uoscode = a1.uoscode
);
```

### Exercise 3: Enrolled Without Assessment
> **Question**: Find the cases of a student and a course, where the student is enrolled in the course and has not received any assessments in that course.

```sql
-- Solution using NOT EXISTS on enrolled:
SELECT sid, uoscode
FROM enrolled e
WHERE NOT EXISTS (
    SELECT 1
    FROM assessment a
    WHERE a.uoscode = e.uoscode
      AND a.sid = e.sid
);

-- Alternative formulation traversing students and courses:
SELECT s.sid, c.uoscode
FROM students s, courses c
WHERE EXISTS (
    SELECT 1
    FROM enrolled e
    WHERE e.sid = s.sid AND e.uoscode = c.uoscode
)
AND NOT EXISTS (
    SELECT 1
    FROM assessment a
    WHERE a.sid = s.sid AND a.uoscode = c.uoscode
);
```

### Exercise 4: Lecturer Teaching Every 12-Credit Point Course
> **Question**: Find the lecturer, if any, who is teaching every course that is worth 12 credit_points.

Because each course has exactly one lecturer (`courses.lecturer`), we formulate this as:
*"Find the lecturer where there is no 12-credit course that this lecturer does not teach."*

```sql
SELECT *
FROM lecturers l
WHERE NOT EXISTS (
    SELECT 1
    FROM courses c
    WHERE c.credit_points = 12
      AND c.lecturer <> l.empid
);
```

### Exercise 5: Students Enrolled in Every 12-Credit Point Course
> **Question**: Find the students, if any, who are enrolled in every course that is worth 12 credit_points.

Classic relational division with double `NOT EXISTS`:
*"Find students for whom there does not exist a 12-credit course for which there is not an enrollment for that student."*

```sql
SELECT *
FROM students s
WHERE NOT EXISTS (
    SELECT 1
    FROM courses c
    WHERE c.credit_points = 12
      AND NOT EXISTS (
          SELECT 1
          FROM enrolled e
          WHERE e.uoscode = c.uoscode
            AND e.sid = s.sid
      )
);
```
