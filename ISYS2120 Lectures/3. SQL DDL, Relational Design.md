# Part A: SQL DDL & Data Modification

## 1. Schema Definition & DDL Fundamentals
- **Logical Schema Awareness**:
  - A relational DBMS is strictly schema-first: data cannot be stored unless the logical schema is already defined.
  - *Contrast*: Schemaless platforms (e.g. JSON document stores, NoSQL) can accept unstructured/semi-structured data first and infer or declare structure post-hoc.
- **Data Definition Language (DDL)**:
  - The subset of SQL used to define, alter, and delete database structures.
  - Specifies table names, column names, column datatypes, and integrity constraints.
- **System Catalogue (Data Dictionary)**:
  - The DBMS stores metadata (schema descriptions, column definitions, constraints, indexes) in internal system catalog tables.
  - The system catalogue can itself be queried via standard SQL `SELECT` statements (e.g., querying tables providing information about attributes across all tables).
- **Schema Namespaces**:
  - Multi-user DBMS servers host multiple users and data owners concurrently.
  - To prevent naming collisions, SQL organizes tables into **schemas** (namespaces):
    - Full table identifier: `schemaname.tablename`
    - Created via: `CREATE SCHEMA schemaname;`
    - If omitted, SQL implicitly resolves tables to the default schema named after the currently authenticated database user.

## 2. Base Datatypes in SQL

| Category | Datatypes | Description | Example Values |
| :--- | :--- | :--- | :--- |
| **Integers** | `SMALLINT`<br>`INTEGER`<br>`BIGINT` | Whole numeric values of varying byte widths | `1704`, `4070` |
| **Fixed-Point Numbers** | `DECIMAL(p, q)`<br>`NUMERIC(p, q)` | Exact fixed-point numbers with $p$ total digits of precision and $q$ decimal places | `1003.44`, `160139.9` |
| **Floating-Point Numbers** | `FLOAT(p)`<br>`REAL`<br>`DOUBLE PRECISION` | Inexact floating-point numbers with precision $p$ | `1.5E-4`, `10E20` |
| **Character Strings** | `CHAR(q)`<br>`VARCHAR(q)`<br>`CLOB(q)` | Fixed-length string of size $q$ (padded with spaces)<br>Variable-length string up to $q$ chars<br>Character Large Object (unbounded text) | `'ISYS2120'`<br>`'The quick brown fox...'` |
| **Binary Strings** | `BLOB(r)` | Binary Large Object / raw byte array of size $r$ | `B'01101'`, `X'9E'` |
| **Temporal / Dates** | `DATE`<br>`TIME`<br>`TIMESTAMP`<br>`INTERVAL` | Calendar date (`YYYY-MM-DD`)<br>Time of day (`HH:MI:SS`)<br>Date and time combined<br>Span of time | `DATE '2026-08-20'`<br>`TIME '20:30:45'`<br>`TIMESTAMP '2026-08-20 14:15:00'`<br>`INTERVAL '11:15' HOUR TO MINUTE` |

> [!NOTE]
> SQL identifiers (table and column names) are **case-insensitive** and cannot contain hyphens `-` (which represent subtraction). Reserved SQL keywords (such as `DATE`, `USER`, `TABLE`) should **not** be used as column or table names. Line breaks and indentation in SQL DDL are not significant.

## 3. The Special `NULL` "Value" & Trade-offs
- **Concept**: A special marker placed in a column to represent facts that are **unknown** (e.g. date of birth not yet recorded) or **not applicable** (e.g. salary or hire date for unpaid adjunct instructors).
  - Can appear in columns of any datatype unless explicitly prohibited.
  - Differs strictly from the string `'NULL'` or the empty string `''`.
  - In many database clients, a cell with `NULL` is displayed completely blank/empty.
- **Trade-offs**:

| Advantages | Disadvantages |
| :--- | :--- |
| **Special system handling**: Aggregate functions (`AVG`, `MIN`, `SUM`) automatically skip `NULL` values instead of returning mathematically skewed results. | **Three-Valued Logic (3VL)**: Complicates boolean predicate evaluations (`TRUE`, `FALSE`, `UNKNOWN`). Comparisons like `27 < NULL`, `27 > NULL`, and `NULL = NULL` all yield `UNKNOWN`. |
| Eliminates reliance on arbitrary "sentinel" values (e.g. `age = -1`, which would corrupt average calculations). | **Query writing confusion**: Often leads to subtle logical errors in `WHERE` clauses if developers assume standard two-valued boolean logic. |

## 4. Integrity Constraints (ICs)
An **Integrity Constraint (IC)** is a predicate condition declared in the schema that must hold true for every legal database instance.
- **Enforcement**: Checked automatically by the DBMS whenever rows are inserted, updated, or deleted.
- **Purpose**: Prevents invalid data from entering the database, guards data quality, and ensures the database faithfully mirrors real-world business rules.

```
       [ Client Application ]
                 │  INSERT / UPDATE / DELETE
                 ▼
       ┌──────────────────┐
       │   DBMS Engine    │ ── Checks ICs (PK, FK, NOT NULL, CHECK)
       └──────────────────┘
         │              │
    Valid instance  Violation detected
         │              │
         ▼              ▼
   [ Committed ]   [ Transaction Rolled Back / Error ]
```

### 4.1 `NOT NULL` Constraint
- Prohibits `NULL` in the specified column; a value must always be supplied.
- Appended directly to the column definition:
```sql
CREATE TABLE Instructor (
    lname VARCHAR(20) NOT NULL,
    fname VARCHAR(20) NOT NULL,
    salary INTEGER,
    birth DATE NOT NULL,
    hired DATE
);
```

### 4.2 Primary Key (`PRIMARY KEY`) Constraint
- Enforces entity identity: values must be **strictly unique** across all rows, and **cannot be `NULL`**.
- At most **one** primary key may be declared per table.
- Can be defined using four alternative syntaxes:

```sql
-- 1. Inline column definition (single-column PK only)
CREATE TABLE Student (
    sid INTEGER PRIMARY KEY,
    name VARCHAR(20)
);

-- 2. Table-level constraint clause
CREATE TABLE Student (
    sid INTEGER,
    name VARCHAR(20),
    PRIMARY KEY (sid)
);

-- 3. Named table constraint (Best practice for descriptive error reporting)
CREATE TABLE Student (
    sid INTEGER,
    name VARCHAR(20),
    CONSTRAINT Student_PK PRIMARY KEY (sid)
);

-- 4. Separate alteration added after table creation
CREATE TABLE Student (
    sid INTEGER,
    name VARCHAR(20)
);
ALTER TABLE Student ADD CONSTRAINT Student_PK PRIMARY KEY (sid);
```

#### Composite Primary Key
When no single attribute uniquely identifies a record, a minimal combination of multiple attributes forms the composite primary key.
- **Must** use table-level constraint syntax:
```sql
CREATE TABLE Airplane (
    manufacturer VARCHAR(20),
    serialno INTEGER,
    weight REAL,
    PRIMARY KEY (manufacturer, serialno)
);

CREATE TABLE EnrolledIn (
    sid INTEGER,
    ucode CHAR(8),
    grade INTEGER,
    PRIMARY KEY (sid, ucode)
);
```

### 4.3 `UNIQUE` Constraint (Candidate Keys)
- Specifies that a column or set of columns must have distinct values across rows.
- A table may have multiple `UNIQUE` constraints (representing alternative candidate keys).
- **`NULL` Handling in `UNIQUE`**:
  - *ANSI SQL Standard (SQL:92 / 1999 / 2003)*: A `UNIQUE` constraint prohibits duplicate non-NULL values, but permits multiple rows to have `NULL`.
  - *DBMS Implementations*: Historically, systems like Oracle and older SQL Server allowed at most one `NULL` in a unique column. PostgreSQL allows multiple `NULL` entries by default (and since PostgreSQL 15 provides `UNIQUE NULLS NOT DISTINCT` syntax).

> [!CAUTION]
> **Careful with Extra Constraints**:
> Over-specifying constraints can inadvertently reject legitimate real-world data!
> - *Intended*: A student receives one grade per course $\rightarrow$ `PRIMARY KEY (sid, cid)`.
> - *Flawed addition*: Adding `UNIQUE (sid, grade)` implies a student can receive a specific grade (e.g. `'HD'`) **at most once across their entire academic career**.
> 
> **Brainteaser**:
> ```sql
> CREATE TABLE Test (
>     a INTEGER,
>     b INTEGER UNIQUE,
>     PRIMARY KEY (a, b)
> );
> ```
> Given tuples: `(1, 1), (1, 2), (1, 3), (2, 1), (2, 4)`.
> Is this instance legal?
> **No!** While `(a, b)` pairs are all unique, tuple `(2, 1)` contains `b = 1`, which duplicates `b = 1` in `(1, 1)`, violating `b INTEGER UNIQUE`.

### 4.4 Foreign Key (`FOREIGN KEY`) & Referential Integrity
- Establishes a logical reference from a column in one table (child/referring) to the primary key (or candidate key) of another table (parent/referenced).
- **Referential Integrity**: Guarantees no "dangling references" exist—every non-NULL foreign key value must match an existing primary key value in the referenced table.
- Foreign keys permit `NULL` by default unless explicitly combined with `NOT NULL`.

```sql
-- Inline column syntax
CREATE TABLE Product (
    ProdID INTEGER,
    descr VARCHAR(10),
    SuppID INTEGER REFERENCES Supplier(SuppID) -- or simply REFERENCES Supplier
);

-- Table-level constraint syntax
CREATE TABLE Product (
    ProdID INTEGER,
    descr VARCHAR(10),
    SuppID INTEGER,
    FOREIGN KEY (SuppID) REFERENCES Supplier(SuppID)
);

-- Named table constraint (Recommended)
CREATE TABLE Product (
    ProdID INTEGER,
    descr VARCHAR(10),
    SuppID INTEGER,
    CONSTRAINT Product_FK FOREIGN KEY (SuppID) REFERENCES Supplier(SuppID)
);
```

> [!IMPORTANT]
> If the referenced primary key is composite, the foreign key **must** also be composite, and **only** table-level syntax can be used:
> `FOREIGN KEY (k1, k2) REFERENCES ParentTable(pk1, pk2)`.

### 4.5 `CHECK` Constraints
- Defines a general boolean condition that must evaluate to `TRUE` or `UNKNOWN` (due to NULL) for every row:
```sql
CREATE TABLE Employee (
    empID INTEGER PRIMARY KEY,
    salary INTEGER CHECK (salary > 0),
    uosCode CHAR(8) CHECK (uosCode SIMILAR TO '[A-Z]{4}[0-9]{4}')
);
```
- If a check condition spans multiple columns, it must be specified as a separate table-level constraint:
```sql
CREATE TABLE Contract (
    startDate DATE,
    endDate DATE,
    CONSTRAINT ValidDates CHECK (endDate >= startDate)
);
```

## 5. Modifying Schema Structure
- **Dropping a Table**:
  ```sql
  DROP TABLE Instructor;
  ```
  Completely removes both table definition and all stored tuples from the database.
- **Altering a Table**:
  ```sql
  ALTER TABLE Student ADD COLUMN email VARCHAR(50);
  ALTER TABLE Student ADD CONSTRAINT Student_PK PRIMARY KEY (sid);
  ```

## 6. Data Modification Language (DML)

### 6.1 `INSERT` Statement
Adds new rows into a table:
```sql
-- 1. Insert tuple matching all columns in declaration order
INSERT INTO Student VALUES (12345678, 'Smit');

-- 2. Insert multiple tuples in a single statement
INSERT INTO Student VALUES 
    (12345678, 'Smit'), 
    (12444455, 'Cheng');

-- 3. Insert into specified subset of columns (unmentioned columns receive DEFAULT or NULL)
INSERT INTO Student (sid) VALUES (12345678);

-- 4. Bulk insert from a SELECT query
INSERT INTO StudentArchive 
SELECT * FROM Student WHERE graduation_year < 2020;
```

### 6.2 `UPDATE` Statement
Modifies column values of existing rows satisfying a `WHERE` condition:
```sql
UPDATE table 
SET column = expression [, column2 = expression2] 
[WHERE search_condition];
```
- *Constant assignment*:
  ```sql
  UPDATE UnitOfStudy SET title = 'Awesome Data' WHERE ucode = 'ISYS2120';
  ```
- *Calculated expression*:
  ```sql
  UPDATE UnitOfStudy SET credit_pts = 2 * credit_pts WHERE ucode = 'ISYS2120';
  ```
- *Note*: Updates evaluate expressions using the **prior values** of each row before applying updates.

### 6.3 `DELETE` Statement
Removes existing rows satisfying a `WHERE` filter:
```sql
DELETE FROM Student WHERE name LIKE '%Fekete';
```
- Omitting the `WHERE` clause deletes **all** rows in the table (leaving the empty table schema intact).

## 7. Referential Integrity on Data Modification
When rows are inserted, updated, or deleted, referential integrity between referenced (parent) and referencing (child) tables must be maintained.

```
 Parent: Professor (empid [PK], name)
            ▲
            │ FK: taughtBy references empid
 Child:  UnitOfStudy (uosCode [PK], title, taughtBy [FK])
```

- **Insertion into Child**: If inserting a `UnitOfStudy` with a `taughtBy` value not matching any `Professor.empid`, the DBMS **rejects** the insert.
- **Deletion or PK Update of Parent**: When a `Professor` row is deleted or their `empid` changes:

| Referential Action | Behavior on Delete / Update |
| :--- | :--- |
| **`NO ACTION`** *(Default)* | Rejects the operation and throws a foreign key violation error if referencing child rows exist. |
| **`CASCADE`** | Propagates the operation: deleting the parent automatically deletes all child rows; updating parent PK automatically updates the FK in child rows. |
| **`SET NULL`** | Sets foreign key column in child rows to `NULL` (requires child FK column to be nullable). |
| **`SET DEFAULT`** | Sets foreign key column in child rows to its declared default value (requires child table column to have `DEFAULT`). |

#### SQL Declaration Syntax
Declared on the **referencing (child)** table:
```sql
CREATE TABLE UnitOfStudy (
    uosCode CHAR(8) PRIMARY KEY,
    title VARCHAR(80),
    credit_pts INTEGER,
    taughtBy INTEGER DEFAULT 1,
    CONSTRAINT FK_TaughtBy FOREIGN KEY (taughtBy) 
        REFERENCES Professor(empid)
        ON UPDATE CASCADE
        ON DELETE SET DEFAULT
);
```

# Part B: Relational Design from ER Model (ER-to-Relational Mapping)

## 1. Overview of the Mapping Process
Logical database design transforms a conceptual model (ER/EER diagram) into a set of relational schemas (tables, columns, primary keys, foreign keys, and integrity constraints).
- **Correctness Criteria**:
  - Every valid real-world state representable in the ER diagram must be representable in the relational schema.
  - Constraints must prevent invalid domain states that violate ER specifications.
- **Golden Rule**:
  > [!WARNING]
  > **Relation $\neq$ Relationship!**
  > In an ER diagram, entity types **never** hold foreign key attributes of other entities. Interconnections are modeled strictly via relationship diamonds. In contrast, relational schemas **must** represent associations through foreign keys.

---

## 2. Mapping Entity Types

### 2.1 Strong Entity Sets
- Each strong entity type maps directly to a **relational table**.
- **Simple attributes** map to columns.
- **Primary key** of the entity set becomes the primary key of the table.
- **Composite attributes** are **flattened** into their simple components:
  - ER: `Employee(address(street, city, state, zipcode))`
  - SQL: `Employee(`<u>`empId`</u>`, name, street, city, state, zipcode)`
- **Multi-valued attributes**:
  - Cannot be stored as a list/array in a relational column.
  - Mapped into an **independent table** containing:
    1. A foreign key referencing the owner entity's primary key.
    2. A column holding an individual attribute value.
  - **Primary Key**: Composite of **all columns** in this table.
  ```sql
  -- Entity Table
  CREATE TABLE Employee (
      empId INTEGER PRIMARY KEY,
      name VARCHAR(50),
      street VARCHAR(50),
      city VARCHAR(30),
      state CHAR(3),
      zipcode VARCHAR(10)
  );

  -- Multi-valued attribute table
  CREATE TABLE EmployeeSkills (
      empId INTEGER,
      skill VARCHAR(30),
      PRIMARY KEY (empId, skill),
      FOREIGN KEY (empId) REFERENCES Employee(empId) ON DELETE CASCADE
  );
  ```

### 2.2 Weak Entity Sets
- Weak entities have no independent primary key and rely on an identifying owner entity via an identifying relationship.
- **Mapping rules**:
  1. Create a separate table for the weak entity.
  2. Include all simple and flattened attributes of the weak entity.
  3. Include a foreign key referencing the primary key of the owner entity (`NOT NULL`).
  4. **Primary Key**: Composite of the owner's primary key (FK) + the weak entity's **partial key (discriminator)**.
```sql
CREATE TABLE Dependent (
    empId INTEGER,
    given VARCHAR(30),
    family VARCHAR(30),
    birthdate DATE,
    PRIMARY KEY (empId, given, family),
    FOREIGN KEY (empId) REFERENCES Employee(empId) ON DELETE CASCADE
);
```

## 3. Mapping Relationships

### 3.1 Many-to-Many ($M:N$) Relationships
Must be mapped using a dedicated **relationship / join table**:
- **Columns**: Foreign keys referencing the primary keys of all participating entity tables + any descriptive attributes of the relationship.
- **Primary Key**: Composite of all participating foreign keys.
- **Foreign Keys**: Each participating foreign key is declared `NOT NULL`.

```sql
-- M:N between Student and UnitOfStudy
CREATE TABLE Enroll (
    sid INTEGER,
    ucode CHAR(8),
    semester VARCHAR(10),
    grade CHAR(2),
    PRIMARY KEY (sid, ucode),
    FOREIGN KEY (sid) REFERENCES Student(sid),
    FOREIGN KEY (ucode) REFERENCES UnitOfStudy(ucode)
);
```

### 3.2 Many-to-One ($N:1$) / One-to-Many ($1:N$) Relationships
There are two alternative design strategies:

#### Approach 1: Separate Join Table
- Create a join table containing FKs to both entities + relationship attributes.
- **Primary Key**: Only the FK from the **many-side** entity (since each instance on the many-side associates with at most one instance on the one-side).
  - e.g. For `Employee` ($N$) $\rightarrow$ `Department` ($1$): Table `WorksIn(`<u>`ssn`</u>`, did, since)`.

#### Approach 2: Embedded Foreign Key (Standard / Preferred Approach)
- Rather than introducing an extra table and requiring expensive joins, add the foreign key directly to the table on the **many-side**:
  - The many-side entity table gets an extra column: FK referencing the one-side table's PK.
  - Any relationship attributes are also added as columns in the many-side table.
  - The primary key of the many-side table remains unchanged.
- **Enforcing Participation**:
  - If participation on the many-side is **total** (thick line / thick arrow $\Rightarrow$), the foreign key column **must** be declared `NOT NULL`.
  - If participation is **partial**, the foreign key column is nullable (`NULL` represents lack of relationship).

```sql
-- Department (One-side)
CREATE TABLE Department (
    did INTEGER PRIMARY KEY,
    dname VARCHAR(50)
);

-- Employee (Many-side with foreign key referencing Department)
CREATE TABLE Employee (
    ssn INTEGER PRIMARY KEY,
    name VARCHAR(50),
    did INTEGER NOT NULL,  -- NOT NULL enforces total participation
    since DATE,
    FOREIGN KEY (did) REFERENCES Department(did)
);
```

### 3.3 Unary (Recursive) Relationships
- A relationship where an entity type is associated with itself in different roles.
- Follows the $N:1$ embedded mapping rule by adding a **self-referencing foreign key** to the entity's table:
```sql
CREATE TABLE Employee (
    ssn INTEGER PRIMARY KEY,
    name VARCHAR(50),
    manager INTEGER,  -- FK referencing another Employee's ssn
    FOREIGN KEY (manager) REFERENCES Employee(ssn)
);
```

### 3.4 Ternary Relationships
- Connects three entity types simultaneously.
- Mapped to a dedicated relation containing foreign keys to all three participating entities plus descriptive attributes:
```sql
CREATE TABLE Ships (
    PartID INTEGER,
    VendorID INTEGER,
    WarehouseID INTEGER,
    when TIMESTAMP,
    PRIMARY KEY (PartID, VendorID, WarehouseID),
    FOREIGN KEY (PartID) REFERENCES Part(PartID),
    FOREIGN KEY (VendorID) REFERENCES Vendor(VendorID),
    FOREIGN KEY (WarehouseID) REFERENCES Warehouse(WarehouseID)
);
```

## 4. Mapping Generalisation / Specialisation (IsA Hierarchies)

```
             ┌──────────────┐
             │    Person    │ (name [PK], street, city)
             └──────┬───────┘
                    │
                  ▲ ISA
                 / \
   ┌────────────┘   └─────────────┐
┌──────────┐                 ┌──────────┐
│ Employee │                 │ Customer │
└──────────┘                 └──────────┘
 (salary)                   (credit_rating)
```

Three alternative mapping techniques exist, depending on hierarchy constraints:

### Approach 1: Distinct Relations (Works Always / Standard)
- Create one relation for the superclass, and separate relations for each subclass.
- **Superclass Table**: Contains primary key and all common attributes.
- **Subclass Tables**: Contains subclass-specific attributes, plus the **superclass primary key**.
  - In each subclass table, this attribute acts simultaneously as the **Primary Key** and as a **Foreign Key** referencing the superclass table.

```sql
CREATE TABLE Person (
    name VARCHAR(50) PRIMARY KEY,
    street VARCHAR(50),
    city VARCHAR(30)
);

CREATE TABLE Employee (
    name VARCHAR(50) PRIMARY KEY,
    salary INTEGER,
    FOREIGN KEY (name) REFERENCES Person(name) ON DELETE CASCADE
);

CREATE TABLE Customer (
    name VARCHAR(50) PRIMARY KEY,
    credit_rating INTEGER,
    FOREIGN KEY (name) REFERENCES Person(name) ON DELETE CASCADE
);
```

### Approach 2: Subclass-Only Relations (Alternative for Total Covering)
- **Applicability**: Only valid when the hierarchy has a **total covering constraint** (every entity in the superclass belongs to at least one subclass).
- **Structure**: Eliminate the superclass table entirely. Create distinct tables only for subclasses.
  - Each subclass table contains its specific attributes **plus all inherited attributes** from the superclass.
  - Primary key of each subclass table is the superclass PK.
  - No foreign keys are needed to represent inheritance.
- *Downside*: Redundancy if subclasses overlap (an entity belonging to multiple subclasses will have duplicated common attributes across tables).

### Approach 3: Single Master Relation (Alternative for Disjoint Subclasses)
- **Applicability**: Best suited when subclasses are **disjoint** and have few subclass-specific attributes.
- **Structure**: Create a single table for the entire hierarchy.
  - Contains all superclass attributes, all attributes of all subclasses, plus an additional **type discriminator** column (e.g. `person_type VARCHAR(10)`).
  - Subclass-specific columns are assigned `NULL` whenever a row represents an entity of a different subclass.
- *Downside*: Introduces widespread `NULL` values and weakens attribute domain enforcement.

## 5. Summary: ER to Relational Correspondence

| ER Conceptual Model | Relational Schema Concept |
| :--- | :--- |
| **Entity Set** | Table (Relation) |
| **Entity Instance** | Row (Tuple) |
| **Simple Attribute** | Column (Attribute) |
| **Entity Primary Key** | Table Primary Key (`PRIMARY KEY`) |
| **Composite Attribute** | Multiple flattened columns |
| **Multi-Valued Attribute** | Separate table with `(Owner_FK, Value)` as composite PK |
| **Weak Entity Set** | Separate table with `(Owner_FK, Discriminator)` as composite PK |
| **$M:N$ Relationship** | Separate join table with composite PK of participating FKs |
| **$N:1$ Relationship** | Foreign key column embedded in the many-side table |
| **Total Participation ($\Rightarrow$)** | `NOT NULL` constraint on the corresponding foreign key |
| **Key Constraint ($\rightarrow$)** | Unique / PK assignment on relationship endpoint |
| **IsA Hierarchy** | Separate subclass tables with superclass PK as PK and FK |

### Checking a Relational Design
1. **Sample Domain States**: Test concrete sample instances against the schema to ensure valid states can be stored.
2. **Constraint Enforcement**: Verify that each business rule in the ER diagram is enforced by a corresponding schema constraint (`PK`, `FK`, `NOT NULL`, `UNIQUE`, `CHECK`).
3. **Nullability Verification**: Ensure nullable columns align with partial participations, and mandatory associations are guarded by `NOT NULL`.
4. **Avoid Dangling References**: Verify that every foreign key correctly identifies its parent table and columns, and referential actions (`CASCADE`, `SET NULL`, `NO ACTION`) match organizational policies.
