## 1. Processes & The Unix Kernel

### What is a Process?
- **A process is a running instance of a program.**
- It consists of:
  - **Code**: The program instructions stored in memory.
  - **Data**: Program variables, dynamic allocations, etc.
  - **Metadata**: Owner ([[UID]]), process ID (PID), open files (file descriptors), state, etc.

> **Analogy:**
> - **Recipe** (program) vs **Cooking the recipe** (process)
> - `cat` is a program; running `cat $filename` creates a process
> - **Docker Image** $\approx$ Program
> - **[[Container|Docker Container]]** $\approx$ Process

### The Unix Kernel & CPU Sharing
- A Unix system holds multiple programs in memory at the same time.
- On a **single-CPU system**, only **one** program can execute at any given instant.
- The **Unix Kernel** is responsible for rapidly switching execution between programs.
- This switching occurs via hardware **interrupts**:
  1. A running program is interrupted by the CPU.
  2. All of its **state** (CPU register contents, program counter, memory state) is saved.
  3. The kernel runs scheduler tasks and switches to another process.
  4. Later, the kernel restores the saved state and restarts the program transparently.

## 2. Standard File Descriptors (FD)

Every process begins with three default open file descriptors:

| FD | Name | Purpose | Default Device |
|:--:|:----:|:-------:|:--------------:|
| `0` | `stdin` | Standard Input | Keyboard / Terminal (`/dev/pts/*`) |
| `1` | `stdout` | Standard Output | Display / Terminal (`/dev/pts/*`) |
| `2` | `stderr` | Standard Error | Display / Terminal (`/dev/pts/*`) |

### Inspecting File Descriptors
Under Linux, you can view a process's open file descriptors in the `/proc` filesystem:
```bash
# View file descriptors for process ID 396:
$ ls -l /proc/396/fd
total 0
lrwx------ 1 user group 64 Aug 30 17:36 0 -> /dev/pts/0
lrwx------ 1 user group 64 Aug 30 17:36 1 -> /dev/pts/0
lrwx------ 1 user group 64 Aug 30 17:36 2 -> /dev/pts/0
# All three descriptors (0, 1, 2) are connected to the pseudo-terminal /dev/pts/0
```

### Redirection Examples
```bash
# Redirect stderr (FD 2) to a log file:
$ command 2> error.log

# Redirect stdout (FD 1) to out.txt, and merge stderr (FD 2) into stdout (FD 1):
$ command > out.txt 2>&1
```

## 3. Process ID (PID) & Monitoring

- Every process in the OS is assigned a unique identifier called the ==**Process ID (PID)**==.
- The kernel uses the PID to identify, track, and manage each process.

### The `ps` Command
Reports a snapshot of the currently running processes:
```bash
$ ps
    PID TTY          TIME CMD
  86272 ttys000   0:00.02 -zsh
  86283 ttys000   0:00.01 bash

# ps columns:
# - PID:  Process ID
# - TTY:  Controlling terminal (each parallel terminal session gets a distinct TTY, e.g. ttys001)
# - TIME: Total CPU execution time consumed by the process
# - CMD:  Command / executable name
```

### Special Shell Variables for PIDs
```bash
# Current process PID (the running shell):
$ echo $$
22337

# PID of the most recent background job (run with &):
$ sleep 60 &
[1] 22775

$ echo $!
22775
```

## 4. Process Hierarchy: Parent & Child Processes (PPID)

- Every process (except the very first process) is started by another process.
- ==**PPID (Parent Process ID)**== identifies the process that created the current process.
- PPID allows the operating system to construct a **process hierarchy (process tree)**.

### `init` / `systemd` (PID 1)
- After the kernel is loaded into memory at boot, it launches the **`init`** process (or `systemd`).
- `init` has **`PID = 1`** and **`PPID = 0`** (it has no parent).
- All processes on the system are descendants of `init`.

```text
init (PID 1, PPID 0)
└── /lib/systemd/systemd --user (PID 1030)
    └── /usr/libexec/gnome-terminal-server (PID 2234)
        └── bash (PID 2260)
            └── ps (PID 2642)
```

### Viewing Process Trees and Details
```bash
# Full format listing (-f):
$ ps -f
UID        PID  PPID  C STIME TTY          TIME CMD
ashekah+   396   395  0 Aug29 pts/0    00:00:01 -bash
ashekah+ 20777   396  0 22:06 pts/0    00:00:00 ps -f
# C:     CPU utilization percentage
# STIME: Process start time

# Custom output columns:
$ ps -o pid,ppid,user,cmd -p $$

# Visual process tree:
$ pstree
$ pstree -p    # includes PIDs
```

### Subshells & `$BASHPID`
Running commands enclosed in `( ... )` spawns a **subshell** (a child process of the current shell):
```bash
$ a="Spring time"

# Inside subshell:
$ ( a="week5"; echo $$; echo $BASHPID; echo $PPID )
2099       # $$ still reflects the parent shell PID!
2132       # $BASHPID correctly reports the subshell's own PID
2099       # $PPID points to the parent shell (2099)

# Variables modified in a subshell do not affect the parent shell:
$ echo $a
Spring time
```

## 5. Processes in Containers & PID [[Namespace]]

- Containers isolate processes using Linux **namespaces**.
- When running a container (e.g. Alpine Linux in Docker):
  ```bash
  $ docker run -it alpine
  / # ps
  PID   USER     TIME  COMMAND
    1   root     0:00  /bin/sh
    7   root     0:00  ps
  ```
- **PID Namespace Virtualization:**
  - **Inside the container:** The root process runs as **PID 1** within its own isolated PID namespace.
  - **On the host machine:** The exact same process appears under a regular host PID (e.g. `PID 21915`, `PPID 21854`).

## 6. Inter-Process Communication (IPC): Signals

- Processes communicate asynchronously by sending **Signals**.
- Signals are dispatched using the `kill` command.

### Permission Rules for Signals
A process can send a signal to another process **only if**:
1. Both the sender and receiver process have the **same [[UID]]**, OR
2. The sender is the **superuser (`root`)**.

### Common Signals (`kill -l`)
```bash
$ kill -l
 1) SIGHUP      2) SIGINT      3) SIGQUIT     9) SIGKILL
15) SIGTERM    18) SIGCONT    19) SIGSTOP
```

- **`SIGTERM` (15)**: Termination request. Can be caught, handled, or cleaned up by the process (polite shutdown). Default signal for `kill`.
- **`SIGKILL` (9)**: Immediate forced kill handled directly by the kernel. Cannot be caught or ignored.
- **`SIGINT` (2)**: Interrupt signal generated by pressing `Ctrl + C` in the terminal.
- **`SIGSTOP` (19)** & **`SIGCONT` (18)**: Pause (suspend) and resume execution.

```bash
# Start background sleep:
$ sleep 60 &
[1] 509

# Send SIGTERM to terminate process 509:
$ kill -SIGTERM 509
[1]+  Terminated              sleep 60
```

## 7. Memory Management: Process Memory Layout

When a program is loaded into memory to run as a process, it is organized into distinct segments:

```text
High Address
┌───────────────────────────────┐
│             STACK             │  ↓ Grows downwards (function call frames,
├───────────────────────────────┤    local/temporary variables)
│               ↓               │
│                               │
│               ↑               │
├───────────────────────────────┤  ↑ Grows upwards (dynamic memory allocation,
│             HEAP              │    e.g. malloc, objects, data structures)
├───────────────────────────────┤
│    STATIC & GLOBAL DATA       │  Initialized & uninitialized global/static variables
├───────────────────────────────┤
│   PROGRAM CODE INSTRUCTIONS   │  Compiled machine code (Text segment, read-only)
└───────────────────────────────┘
Low Address (Address 0)
```

## 8. Memory Mapping: Logical vs Physical Addresses

### The Problem
How can every process believe its memory starts at **address 0** without overwriting other processes in RAM?

### The Solution: Address Translation (MMU)
- The CPU hardware contains a memory management unit that **remaps** the address space for each process while it runs.
- **Logical (Virtual) Address**: The memory addresses referenced by the process code (starting from 0).
- **Physical Address**: The actual electrical hardware memory locations in physical RAM chips.

> **Early Scheme (Base & Limit / Offset Register):**
> - The OS kernel uses privileged CPU instructions to set a special base register.
> - If a process is located starting at physical RAM address `1000`, the offset is set to `1000`.
> - Any reference to logical address `0` automatically translates to physical address `1000` ($0 + 1000$).

## 9. Virtual Memory & The Page Table

### Pages and Frames
- Rather than mapping an entire contiguous block for each process, modern operating systems divide memory into small, fixed-size blocks called ==**Pages**==.
- Physical memory is divided into corresponding slots called **Page Frames**.
- Memory pages do not need to be stored contiguously in physical RAM, and can be shared or interleaved with other processes.

### The Page Table
- The kernel maintains a **Page Table** for each process.
- Maps the **virtual address of a page** to either:
  1. A **physical memory address** in RAM, OR
  2. An address indicating the page is stored on **mass storage (disk / swap)**.

| Process ID | Process (Virtual) Address | Physical Memory Address (RAM) | Mass Storage Address (Disk) |
|:----------:|:-------------------------:|:-----------------------------:|:---------------------------:|
| 1456 | `100000` | `12000000` | `0` (Resident in RAM) |
| 1456 | `120000` | `0` (Not in RAM) | `32100` (Swapped to disk) |

## 10. Swapping, Page Faults, and Thrashing

### What happens when accessing memory mapped to disk? (Page Fault)
1. **Interrupt (Page Fault):** The CPU detects that the virtual page is not currently in physical RAM and triggers a hardware interrupt.
2. **State Saved:** Execution freezes and the process state is saved. Control transfers to the kernel.
3. **Swap In:** The kernel locates the required page on disk in the **swap area** and reads it into an available free page frame in RAM.
4. **Update Page Table:** The kernel updates the process's page table with the new physical RAM address.
5. **Resume Execution:** The kernel restores the process state and restarts the interrupted instruction. The process continues with no awareness that an interruption occurred.

### Page Eviction (Swapping Out)
- If the kernel needs to bring a page into RAM but **all physical memory is full**, it must choose an existing page in RAM and write it out to the **swap area** on disk to free up space.

### Thrashing
- **Disk access is thousands of times slower than RAM.**
- If physical memory is critically low and pages are constantly being swapped back and forth between RAM and disk, the system becomes extremely sluggish.
- This state of excessive paging is known as ==**thrashing**== (the CPU spends more time waiting for disk I/O than executing user instructions).
