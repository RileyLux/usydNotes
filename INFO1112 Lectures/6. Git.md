## 1. Introduction to Git & Version Control

- ==**Git**== is a distributed command-line version control system designed to track changes in source code over time.
- Created by **Linus Torvalds** (creator of Linux) in 2005:
  > *"It's more popular than Linux."* — Linus Torvalds
- Instead of saving just differences/deltas, Git takes **"snapshots"** of the entire codebase at specific points in time.

---

## 2. Core Problems Git Solves (Features of Git)

### 1. Code Synchronization Across Team Members
- In a team, multiple developers work on the same codebase simultaneously on their local machines.
- Git allows code to be synchronized via a shared **central repository** (hosted online):
  - Developers make changes locally.
  - They **push** changes to the remote repository.
  - Other team members **pull** those updates to keep their local environments synchronized and up-to-date.

```text
       [ Developer 1 (Local) ]
                 │ (push)
                 ▼
       ┌───────────────────┐
       │ Remote Repository │ (e.g., GitHub)
       └───────────────────┘
                 │ (pull)
                 ▼
       [ Developer 2 (Local) ]
```

### 2. Code Testing Without Losing the Original (Branching & Merging)
- Developers often want to experiment with new ideas or features without breaking the working version of the code.
- **Branches:** Git lets you create an isolated copy of the code on a separate ==**branch**== to test ideas safely.
- **Merging:** Once the changes are tested and verified, they can be ==**merged**== back into the stable original branch (e.g., `main`).

```text
Stable Branch (main) ──●──────────────●──────────────● (Merged)
                        \                            /
                         └──● (Test feature) ──●────/
                            Feature Branch
```

### 3. Reverting to Older Versions of Code (Rollback)
- If a recent change introduces bugs, unwanted behavior, or a change of mind:
- Git allows you to ==**revert back**== to any previously saved commit state in the project's history.

## 3. Git vs. GitHub

| Feature / Concept | **Git** | **GitHub** |
| :--- | :--- | :--- |
| **What it is** | Command-line tool & version control system | Cloud hosting platform / web service |
| **Where it runs** | Locally on your computer (Linux/macOS/Windows) | Remotely on the web / cloud servers |
| **Purpose** | Records snapshots, manages branches, tracks history | Stores remote Git repositories, enables team collaboration |
| **Alternatives** | Mercurial, SVN (Subversion) | GitLab, Bitbucket |

### Creating a GitHub Repository
1. Navigate to `github.com/new`.
2. Configure repository settings:
   - **Owner & Repository Name** (e.g., `INFO1112`).
   - **Description**: Optional summary of the project.
   - **Visibility**:
     - ==**Public**==: Anyone on the internet can see and clone/download the repository, but only authorized contributors can modify/push code.
     - ==**Private**==: Only you and specifically invited collaborators can view or access the repository.
   - Initial files (README, `.gitignore`, License).
3. Click **"Create repository"**.

## 4. Git Architecture: The Three Main Areas

Understanding how Git moves files between states is fundamental:

```text
┌─────────────────────────┐        git add         ┌─────────────────────────┐
│    Working Directory    │ ─────────────────────> │      Staging Area       │
│  (Untracked / Modified) │                        │         (Index)         │
└─────────────────────────┘                        └─────────────────────────┘
                                                                │
                                                                │ git commit
                                                                ▼
┌─────────────────────────┐        git push        ┌─────────────────────────┐
│    Remote Repository    │ <───────────────────── │    Local Repository     │
│        (GitHub)         │ ─────────────────────> │     (.git directory)    │
└─────────────────────────┘        git pull        └─────────────────────────┘
```

1. **Working Directory:** The local folder where you view, edit, and create files.
2. **Staging Area (Index):** The intermediate holding area where files are selected and prepared for the next commit.
3. **Local Repository (`.git`):** The local database storing the full commit history and metadata on your machine.
4. **Remote Repository:** The hosted copy on GitHub accessible to the team.

## 5. Core Git Commands & Workflow

### 1. `git clone <url>` — Downloading a Repository
- Downloads a remote repository from GitHub/Internet onto your local machine.
- Creates a local directory containing the repository files and the hidden `.git` tracking folder.
- **URLs & Authentication:**
  - **HTTPS:** `https://github.com/<user>/<repo>.git` (requires Personal Access Token or credential manager).
  - **SSH:** `git@github.com:<user>/<repo>.git` (requires configured SSH keys).

```bash
# Verify Git installation:
$ git --version
git version 2.55.0

# Clone a remote repository:
$ git clone https://github.com/AhmmedAshek/INFO1112.git
Cloning into 'INFO1112'...
warning: You appear to have cloned an empty repository.

# Navigate into the cloned repository:
$ cd INFO1112/
$ ls
# (Empty initially)
```

---

### 2. `git add <filename>` — Staging Files
- Informs Git which files should be included in the next "save point" (commit).

> **Why two separate steps (Selection vs. Save)?**
> - In a real project directory, you may edit or create many temporary, log, or test files.
> - You only want to commit specific, logical sets of changes (e.g., `assembler.sh` and `emulator.sh`), keeping the commit history clean and purposeful.

```bash
# Create a new script file:
$ touch loganalyze.sh

# Stage the file for the next commit:
$ git add loganalyze.sh
```

---

### 3. `git commit -m "<message>"` — Creating Snapshots
- Records a permanent snapshot of the currently staged files into the local repository history.
- **Commit Message (`-m`):** A descriptive "note to yourself and team" explaining *what* changed and *why*.
  - Essential when searching or reverting history later.

```bash
$ git commit -m "the loganalyze.sh script was created"
[main (root-commit) 1db46df] the loganalyze.sh script was created
 1 file changed, 17 insertions(+)
 create mode 100644 loganalyze.sh
```

#### Breakdown of Git Commit Output:
- **`main`**: The current branch name.
- **`(root-commit)`**: Indicates this is the initial (first) commit in the repository hierarchy with no parent commit.
- **`1db46df`**: Abbreviated 7-character hexadecimal SHA commit identifier.
- **`1 file changed, 17 insertions(+)`**: Summary of modified files and added lines.
- **`create mode 100644`**:
  - `100`: Regular file format (vs directory or symlink).
  - `644`: Standard Unix octal permissions:
    - User/Owner: Read (`4`) + Write (`2`) = `6` (`rw-`)
    - Group: Read (`4`) = `4` (`r--`)
    - Others: Read (`4`) = `4` (`r--`)

> [!IMPORTANT]
> **Commits are strictly local!**
> Making a commit does **not** update the remote repository on GitHub. Files will not appear on GitHub until you explicitly run `git push`.

### 4. `git status` — Checking Repository State
- Displays the working tree status: current branch, tracked vs untracked files, staged changes, and synchronization status relative to remote.

```bash
$ git status
On branch main
Your branch is ahead of 'origin/main' by 1 commit.
  (use "git push" to publish your local commits)

nothing to commit, working tree clean
```
- **`ahead by 1 commit`**: You have made 1 local commit that hasn't been uploaded to GitHub yet.

- Compresses and uploads local commits and referenced objects to the remote repository on GitHub.

### 6. Updating Files & the `-a` Flag (`git commit -am`)
- When modifying an already tracked file:

```bash
$ git status
On branch main
Your branch is up to date with 'origin/main'.

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   loganalyze.sh

no changes added to commit (use "git add" and/or "git commit -a")
```

- **Shortcut (`-a` with `-m`):**
  - The `-a` (`--all`) flag automatically stages **all modified or deleted tracked files** before committing.
  - *Note:* It does **not** stage newly created (untracked) files.

```bash
$ git commit -am "Added the find log files part"
[main bc0c79a] Added the find log files part
 1 file changed, 6 insertions(+), 1 deletion(-)
```

### 7. Remote Synchronization: `git fetch` vs `git pull`

#### The Problem:
- If another team member commits and pushes code to GitHub (or changes are made directly on the GitHub web editor):
- Running `git status` locally **will not automatically detect remote changes** because it only checks local tracking references without querying the internet:
  ```bash
  $ git status
  On branch main
  Your branch is up to date with 'origin/main'.
  nothing to commit, working tree clean
  ```

#### `git fetch`:
- Connects to the remote repository and **downloads the latest metadata, branch references, and commits without modifying your local working files or current branch**.
- After fetching, `git status` accurately reflects the remote state:

```bash
$ git fetch
remote: Enumerating objects: 5, done.
remote: Counting objects: 100% (5/5), done.
remote: Compressing objects: 100% (2/2), done.
remote: Total 3 (delta 1), reused 0 (delta 0), pack-reused 0 (from 0)
Unpacking objects: 100% (3/3), 1.00 KiB | 256.00 KiB/s, done.
From https://github.com/AhmmedAshek/INFO1112
   bc0c79a..9cd160b  main       -> origin/main

$ git status
On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)
```

#### `git pull`:
- Fetches changes from the remote repository and **immediately merges / integrates them** into the current local working branch.
- Updates working files to match the remote version (often via a *fast-forward* merge).

```bash
$ git pull
Updating bc0c79a..9cd160b
Fast-forward
 loganalyze.sh | 7 +++++++
 1 file changed, 7 insertions(+)
```

## 6. Quick Reference: Core Git Commands Summary

| Command | Action / Description | Key Notes |
| :--- | :--- | :--- |
| `git clone <url>` | Downloads a remote repo to local machine | Sets up remote tracking branch `origin` |
| `git status` | Displays working tree and staging area state | Shows untracked, modified, staged files |
| `git add <file>` | Adds file changes to the Staging Area | Selective inclusion before committing |
| `git commit -m "<msg>"` | Saves a snapshot of staged changes locally | Strictly local; does not update remote |
| `git commit -am "<msg>"`| Stages modified tracked files and commits | Does not add newly created untracked files |
| `git push` | Uploads local commits to remote repo (GitHub) | Publishes changes for team members |
| `git fetch` | Downloads remote metadata without touching local files | Updates remote tracking references |
| `git pull` | Downloads remote changes and merges into local branch | Equivalent to `git fetch` + `git merge` |
| `git branch <name>` | Creates a new branch for testing/features | Isolates experimental changes |
| `git merge <name>` | Combines changes from another branch | Integrates tested code back into `main` |

## 7. Inspecting History & Rolling Back

### 1. `git log` — Inspecting Commit History
- Displays the chronological commit history of the repository in reverse order (most recent commit at the top).
- Provides essential metadata for tracking, auditing, and inspecting past states:
  - **Commit Hash (SHA-1):** A 40-character unique hexadecimal checksum identifying the snapshot (e.g., `cb079f1ee8b02888a3104f7214f6324617a6c12c`).
  - **Branch & HEAD Pointers:** Indicates where `HEAD`, local branches (`main`), and remote branches (`origin/main`) are currently pointing.
  - **Author:** Name and email of the developer who created the commit.
  - **Date & Timestamp:** Exact date, time, and timezone of commit creation.
  - **Commit Message:** Descriptive log explaining what changes were introduced.

```bash
$ git log

Author: AhmmedAshek <ashek.ahmmed@sydney.edu.au>
```

### 2. `git reset` — Reverting to an Older State
- Allows you to revert the entire repository back to an earlier historical commit snapshot.
- Useful when a recent change introduces breaking bugs, crashes, or unwanted modifications.

#### The `--hard` Flag:
- ==`--hard`== performs a hard reset, resetting **everything**:
  1. The **Working Directory** (local files).
  2. The **Staging Area (Index)**.
  3. The **`HEAD` pointer** (moves back to the chosen commit).

```text
               git reset --hard <commit-hash>
               ┌─────────────────────────────┐
               ▼                             │
  Commit 1 ────────> Commit 2 ────────> Commit 3 (Buggy / Broken)
  (57656c6)          (436f6d6)          (Latest)
   [OK]               [Rollback Target]
```

#### Two Common Ways to Use `git reset --hard`:
1. **Resetting to a Specific Commit Hash:**
   - Find the target commit hash using `git log` and pass it to `git reset`:
   ```bash
   $ git reset --hard 57656c6
   HEAD is now at 57656c6 Add line
   ```
2. **Reverting Local Repo to Match GitHub (`origin/main` / `origin/master`):**
   - Discards all local commits and uncommitted edits, instantly bringing the local repository in sync with the remote repository version:
   ```bash
   $ git reset --hard origin/main
   ```

> [!CAUTION]
> **Data Loss Warning with `git reset --hard`:**
> Any uncommitted edits and all commits made after the target commit hash will be permanently removed from your working tree. Ensure you want to completely discard those changes before running this command.

## 8. Branching & Isolated Development

### 1. The Problem with a Linear Working Structure
- In a strictly linear workflow, development proceeds along a single timeline:
  ```text
  (First Commit) ──> (Changes) ──> (More Changes) ──> (Start Feature) ──> (Keep Working)
  ```
- **The Issue:** What happens if you discover a critical bug in an earlier component (e.g., `assembler.sh`) while in the middle of writing a new, unfinished feature (e.g., `emulator.sh`)?
  - You cannot easily test or commit a bug fix without risking mixing in half-baked, broken feature code.
  - Linear workflows create dependency bottlenecks and make team collaboration hazardous.

### 2. The Solution: Parallel Branching
- Instead of working on a single line, Git allows you to branch off into multiple parallel tracks of development.
- **Scenario / Use Case:**
  - You finished `assembler.sh` on `main`.
  - You now start work on `emulator.sh`, which depends on `assembler.sh` output. Because this is an entirely new feature, you start work on a separate branch (`emulator`).
  - If a bug is later discovered in `assembler.sh`, you can switch back to `main` (or a dedicated bugfix branch), resolve and test the fix, and commit it without disturbing your work on `emulator.sh`.

```text
                               ┌──● (Start emulator.sh) ──● (Work on emulator) [emulator branch]
                              /
main ──●──────────────●──────● (Bug discovered)
 (First commit)   (Changes)                                  └──● (Fix bug in assembler.sh) ──● [main branch]
```

---

### 3. Branch Names and `HEAD`
- **Branch Naming Conventions:**
  - ==`main`== (or historically `master`): The default branch containing the stable, production-ready version of your code.
  - ==`feature` branches== (e.g., `emulator`, `login-auth`): Isolated branches used for developing new features, experiments, or patches.
- **What is `HEAD`?**
  - ==`HEAD`== is an internal Git reference pointer that points to the **current branch and commit** you are actively working on in your working directory.
  - If `HEAD` points to `main`, your working tree reflects `main`.
  - When you switch `HEAD` to `emulator`, your working tree shifts focus to `emulator`.

```text
                          ┌──● (Feature commit) ──● [feature] ◄── HEAD (Current Focus)
                         /
main ──●────────●───────● 
                        └──● [master]
```

### 4. Branching Commands & Workflow

#### 1. `git branch` — Inspecting Branches
- Lists all local branches in the repository.
- The asterisk (`*`) indicates the branch where `HEAD` is currently located:
```bash
$ git branch
* main
```

#### 2. `git checkout -b <branch-name>` — Creating & Switching Branches
- Creates a new branch from the current commit and immediately switches `HEAD` to it:
```bash
$ git checkout -b emulator
Switched to a new branch 'emulator'

$ git branch
* emulator
  main
```
- Any subsequent commits made now will only affect `emulator`, leaving `main` completely untouched.

> [!NOTE]
> In modern Git (version 2.23+), `git switch -c <branch-name>` can also be used to create and switch branches.

#### 3. Switching Between Branches (`git checkout <branch-name>`)
- To return to `main` (or switch between branches):
```bash
$ git checkout main
Switched to branch 'main'
Your branch is up to date with 'origin/main'.

$ git branch
  emulator
* main
```

#### 4. How `git checkout` Works Internally:
When you run `git checkout <branch>`, Git performs three operations:
1. **Moves `HEAD`** to point to the designated branch.
2. **Reads the snapshot** from the latest commit on that branch.
3. **Updates the files in your Working Directory** to match that snapshot (files specific to other branches disappear, and files belonging to the selected branch appear).

```bash
# On emulator branch:
$ touch emulator.sh
$ git add emulator.sh
$ git commit -m "emulator is created."
[emulator f6400b0] emulator is created.
 1 file changed, 25 insertions(+)
 create mode 100644 emulator.sh

$ ls
add.bin  add.vsc  assembler.sh  assemblerTestPlan.md  empty.vsc  emulator.sh  prog.bin  prog.vsc

# Switch back to main:
$ git checkout main
Switched to branch 'main'

$ ls
add.bin  add.vsc  assembler.sh  assemblerTestPlan.md  empty.vsc  prog.bin  prog.vsc
# Notice: emulator.sh is not here!
```

> [!TIP]
> **Why is `assembler.sh` available in the `emulator` branch even though it was created in `main`?**
> Because `emulator` was branched off `main` *after* `assembler.sh` was already committed. A branch inherits the complete commit history and file snapshot of its parent branch at the exact moment of branching.

#### 5. `git push -u origin <branch-name>` — Publishing Branches to GitHub
- A newly created local branch does not exist on GitHub until explicitly published.
- The ==`-u`== (`--set-upstream`) flag links the local branch to the remote branch:
```bash
$ git push -u origin emulator
Total 0 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
remote: 
remote: Create a pull request for 'emulator' on GitHub by visiting:
remote:      https://github.com/AhmmedAshek/INFO1112-Assignment-1/pull/new/emulator
remote: 
To https://github.com/AhmmedAshek/INFO1112-Assignment-1.git
 * [new branch]      emulator -> emulator
branch 'emulator' set up to track 'origin/emulator'.
```
- After setting upstream tracking, subsequent uploads or downloads on this branch only require `git push` or `git pull`.

---

### 5. `git merge <branch-name>` — Integrating Branches
- Once work on a branch is tested, verified, and complete, it is merged back into the primary branch (`main`).
- **Merging Steps:**
  1. Switch to the receiving branch:
     ```bash
     $ git checkout main
     ```
  2. Merge the feature branch into `main`:
     ```bash
     $ git merge emulator
     Updating cb079f1..f6400b0
     Fast-forward
      emulator.sh | 25 +++++++++++++++++++++++++
      1 file changed, 25 insertions(+)
      create mode 100644 emulator.sh
     ```
- **Fast-forward Merge:** When no new commits occurred on `main` after branching, Git simply advances the `main` branch pointer directly to the tip of `emulator`.
- All developed code (`assembler.sh` and `emulator.sh`) is now safely united in `main`.

## 9. Handling Merge Conflicts

### 1. What Causes a Merge Conflict?
- A ==**merge conflict**== occurs when two collaborators (or two merging branches) modify the **exact same line(s) of code** in a file, and Git cannot automatically decide which version to use.
- Git automatically handles non-overlapping changes across files or different lines in the same file. But overlapping modifications require manual human intervention.

```text
Collaborator 1 (Local):                                Collaborator 2 (Remote/GitHub):
Edits line 13 to:                                      Edits line 13 to:
"usage: more than 1 (one) arg is not allowed.
"       "usage: more than 1 argument is not allowed.
"
          │                                                       │
          ▼                                                       ▼
  Commit locally                                          Commit on GitHub
          │                                                       │
          └─────────────────────┬─────────────────────────────────┘
                                ▼
                        Run: git pull
                                ▼
                  💥 CONFLICT (content) 💥
```

---

### 2. A Real Conflict Walkthrough

#### Step 1: Local Modification & Commit
- You edit `loganalyze.sh` locally:
```bash
$ nano loganalyze.sh
$ git add loganalyze.sh
$ git commit -m "Described 1 as one"
[main bc1bbd5] Described 1 as one
 1 file changed, 1 insertion(+), 1 deletion(-)
```

#### Step 2: Concurrent Remote Modification
- Meanwhile, a collaborator modifies the exact same line via GitHub's web editor and commits directly to `main` with the commit message `"Described arg"`.

#### Step 3: Pulling Triggers Conflict
- When you run `git pull`, Git attempts an automatic merge and stops:
```bash
$ git pull
Auto-merging loganalyze.sh
CONFLICT (content): Merge conflict in loganalyze.sh
Automatic merge failed; fix conflicts and then commit the result.
```

---

### 3. Anatomy of Conflict Markers
Git injects conflict markers directly into the conflicting file:

```bash
<<<<<<< HEAD (Current Change)
echo -e "usage: more than 1 argument is not allowed.
"
=======
echo -e "usage: more than 1 (one) arg is not allowed.
"
>>>>>>> bc1bbd5 (Described 1 as one) (Incoming Change)
```

- **`<<<<<<< HEAD (Current Change)`**: Start of the conflict block containing changes from your local checked-out branch.
- **`=======`**: Separator line between the conflicting versions.
- **`>>>>>>> <commit-hash> (Incoming Change)`**: End of the conflict block, displaying the incoming commit hash and commit message.

---

### 4. Resolving Conflicts Step-by-Step

#### Step 1: Make a Human Decision
You must decide between three choices:
1. **Keep Local Version:** Retain your changes and discard incoming changes.
2. **Accept Remote Version:** Adopt the remote/incoming changes and discard local changes.
3. **Compromise / Combine:** Manually rewrite the section to combine or reconcile both ideas.

#### Step 2: Use Code Editors (e.g., VS Code)
Modern editors detect Git conflict markers and present one-click options:
- `Accept Current Change`
- `Accept Incoming Change`
- `Accept Both Changes`
- `Compare Changes`

#### Step 3: Stage, Commit, and Push
Once the file has been manually adjusted and all delimiter markers (`<<<<<<<`, `=======`, `>>>>>>>`) have been deleted:

```bash
# 1. Stage the resolved file:
$ git add loganalyze.sh

# 2. Commit the merge resolution:
$ git commit -m "fixed merge conflict"

# 3. Deliver the clean, unified version to GitHub:
$ git push
Enumerating objects: 5, done.
Counting objects: 100% (5/5), done.
Delta compression using up to 10 threads
Compressing objects: 100% (3/3), done.
Writing objects: 100% (3/3), 327 bytes | 327.00 KiB/s, done.
Total 3 (delta 1), reused 0 (delta 0), pack-reused 0 (from 0)
remote: Resolving deltas: 100% (1/1), completed with 1 local object.
To https://github.com/AhmmedAshek/INFO1112.git
   537d485..b4d3b61  main -> main
```

## 10. Key GitHub Collaboration Features

### 1. Fork (`Forking`)
- A ==**Fork**== is an independent, server-side copy of someone else's repository created under your personal GitHub account.
- **Purpose & Benefits:**
  - Allows you to freely experiment and implement changes without affecting the original upstream repository.
  - Essential for contributing to open-source software where you do not have write/push access to the core repository (e.g., `tensorflow/tensorflow`).

```text
Original Upstream Repo (e.g., tensorflow/tensorflow)
               │
               │ (Fork)
               ▼
Personal Copy Repo (e.g., your-username/tensorflow)
               │
               │ (Clone & edit locally)
               ▼
Local Machine Development
```

---

### 2. Pull Requests (PR)
- A ==**Pull Request (PR)**== is a formal proposal asking the maintainers of the original upstream repository to pull changes from your fork/branch into their project.
- **The Open-Source Collaboration Workflow:**
  1. **Fork** the original repository to your GitHub account.
  2. Clone your fork locally, create a feature branch, and commit your improvements.
  3. Push the feature branch back to your personal GitHub fork.
  4. Navigate to GitHub and submit a **Pull Request**.
  5. **Review & Discussion:** Project maintainers inspect code diffs, run continuous integration (CI) tests, give feedback, and request revisions.
  6. **Merge:** Once approved, maintainers merge your PR into the upstream codebase.

> [!NOTE]
> Pull Requests are a fundamental strength of open-source development, enabling asynchronous, global collaboration with high code review standards.

---

### 3. GitHub Pages (Non-Examinable)
- A free hosting service provided by GitHub that builds and serves static websites directly from a repository.
- By naming a repository `<username>.github.io` and adding standard web files (`index.html`, CSS, JS), GitHub automatically deploys and serves the site over HTTPS.

## 11. Quick Reference: Part B Git Commands Summary

| Command | Purpose | Key Details |
| :--- | :--- | :--- |
| `git log` | Displays repository commit history | Lists 40-char SHA commit hashes, author, timestamp, commit messages |
| `git reset --hard <commit>` | Resets repo back to a historical commit | Discards all local uncommitted changes and commits after `<commit>` |
| `git reset --hard origin/main` | Overwrites local changes to match remote | Reverts local repo to the exact state currently hosted on GitHub |
| `git branch` | Lists all local branches | Asterisk (`*`) indicates currently active branch (`HEAD`) |
| `git checkout -b <branch>` | Creates a new branch and switches to it | Combines branch creation and `HEAD` movement |
| `git checkout <branch>` | Switches `HEAD` to target branch | Updates working directory files to match branch snapshot |
| `git push -u origin <branch>` | Pushes new local branch to GitHub | `-u` sets upstream tracking for future simple `git push`/`pull` |
| `git merge <branch>` | Merges changes from `<branch>` into current branch | Fast-forward merge or initiates merge conflict resolution |
