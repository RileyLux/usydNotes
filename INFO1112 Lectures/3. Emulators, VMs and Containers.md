## UID (User ID)/ GID(Group ID)
- A process is a program with its data stored in memory, as well as metadata like owner, open files etc.
- Every Process running has an associated User ID 
- When a process is ran by the shell, it uses the UID of the shell
		- The commands run can access the same files the user has access to, or anything the users group has access to
- ==**/etc/passwd**== file contains translation/mapping between the User ID's used by UNIX kernel, and the Usernames

- ==**/etc/group**== file contains the mapping between the UNIX kernels GID and the group name
- Groups are used to manage permissions to multiple users at once, instead of individually assigning permissions
- Every user in a group has the same permissions as the group, even if their individual user permissions are lower
- **When an account gets created, it also gets assigned to a group of the same name**

```bash
$ cat /etc/passwd
root:x:0:0:root:/root:/:/bin/bash
riley:x:1000:1000::/home/riley:/bin/bash

#UserID: 1000
#GroupID: 1000
#Home directory is /home/riley
#Shell program is at /bin/bash

$ cat /etc/group
root:x:0:
riley:x:1000

#To find the id of UID of the Shell we can use:
$ id
uid=1003(riley) git=1003(riley) groups=1003(riley)
```

## SuperUser ID
- **UID 0** is very special, it has access to any file and can run any program 
	- Also can access any device, as devices are just files in the [[Namespace]]
- Superuser is given the username **root** since this is the first process that is executed by the system
- superuser is very powerful, but also dangerous

## Devices in the [[Namespace]]
- Feature of UNIX was to make access to devices similar to other files
	- Every device is also a file in the namespace
	- Standard read/write/execute/open/close system calls work in the same way for devices as with normal files
- On a UNIX system, the ==**/dev/sda**== is the pathname for the disk drive
	- By opening and reading this, you can access the whole device starting from there\
	- Often needs superuser permissions to access
```bash
$ ls -l /dev/sda
brw-rw---- 1 root disk 8, 0 Jun 23 13:04 /dev/sda
```

## Emulator
- An emulator is a program that reads machine instructions (binary) and interprets or executes them, pretending to be a real CPU.
- It "emulates" instructions, running a program designed for one architecture on another.
- Rather than write binary bits by hand, we use a human-readable shorthand called **assembly language**.
- Assembler: program that reads assembly language instructions and translates them into binary numbers to represent machine instructions

### Machine Instructions Example
A hypothetical 16-bit instruction might be represented as:
```text
# Assembly:
ADD 4, 8, 12

# Binary (Machine Instruction):
01100100 10001100

# Breaking down the binary:
# 0110 -> Opcode for "ADD" instruction
# 0100 -> Address 4
# 1000 -> Address 8
# 1100 -> Address 12
```

### Decoding Process
Emulators need to read this binary and break it down to figure out what to do. They use bitwise operations like **right shifting** and **masking**.

**Step 1: Shift right to isolate the opcode**
```python
# To get the opcode '0110' to the far right, we shift by 12 bits:
0b0110010010001100 >> 12

# The result is:
0b0000000000000110
```

**Step 2: Masking using Logical AND**
```python
# We use a 'mask' to extract only the bits we care about using bitwise AND (&).
# Masking with 1111 (or 0xF in hex) keeps only the last 4 bits:
  0b0000000000000110
& 0b0000000000001111
--------------------
  0b0000000000000110  # Result is 0110

# The emulator then looks up 0110 in its manual, sees it's an ADD operation
# that takes 3 addresses as arguments, and performs the addition.
```

- While emulators provide important insights into system mechanisms, emulated programs generally run very slowly.

## Virtual Machine (VM)
- An emulator generally just emulates CPU instructions and registers. If it also emulates all system aspects like memory management and I/O, it's called a **Virtual Machine**.
- A VM is a complete emulation capable of running an entire operating system (OS).
- **Use Cases**:
  - Run a different OS or version (e.g., Linux on Windows).
  - Run older software.
  - Develop and test software on many different target environments from the same physical machine.
  - Run many small systems in parallel on a single large machine (cloud providers heavily use VMs).
- **Isolation**: VMs have complete isolation.
- **Downsides**: High resource utilization, consumes higher disk space (Gigabytes in size), and has a slower "boot up" time because it has to boot an entire OS.
- Example: **VirtualBox** by Oracle.

## [[Container]]
- Containers provide isolated environments (with their own processes, network interfaces, and mounts) much like VMs.
- **Difference from VMs**: All containers on a host **share the same OS kernel** (e.g., the Linux kernel) which is responsible for interacting with the underlying hardware.
- It is the software *above* the kernel (user interfaces, drivers, compilers, file managers) that makes them different.
- **Advantages**: 
  - Because they share the kernel and don't boot a full OS, containers are very lightweight (Megabytes in size).
  - "Boot up" is much faster compared to a VM.
- Example: **Docker**. 
  - You can run any flavor of OS on top of a Docker host (e.g., Ubuntu, Fedora, openSUSE on an Ubuntu host), with the only catch being they must be based on the same kernel (Linux).
  - You *cannot* run a Windows-based container on an Ubuntu host that has a Linux kernel.
